## 0. TL;DR

- **真因は運動方程式が最小二乗の一項だったこと(§8)。** 単位混在の目的関数で
  摩擦錐の slack と天秤にかけられ、物理を破る方が「安い」解が選ばれていた。
  **EoM を単独最上段に置くだけで G1 が立つ。** ここを先に読むこと。
- **G1(34 kg)** ── 静止 degraded 0 / 傾き 0.11°、**屈伸 150 mm で degraded 0**、
  片足は離地成功だが 0.2 秒後に転倒(§9)。セッション開始時は 0.37 秒で発散
  していた機体。
- **kyo46rs(6.6 kg)** ── 屈伸 degraded 0、片足 degraded 18 / 傾き 2.6°。
- **残る 1 件: 目標がフィードバックで汚染されていた(§9.2)。** `y_ref` を毎 tick
  立脚足リンクから読んでいたため、足首が転がると重心目標が 37 mm 飛ぶ。
  QP は degraded ゼロで忠実に追従して倒れる。`LATCH_STANCE` で対処。
- **耐外乱の律速は着地後の接触喪失(§18)。** CoP 箱でも ankle_roll 可動域でも
  摩擦でも自己干渉でもない ── 4 つとも測って潰した。転倒は「押された量」では
  なく着地位相との相互作用で決まり、**より小さい力積で転ぶ**ことがある。判定量は
  **浮上時間**(両足の合計鉛直力が体重の半分未満の時間、14/14 セルで生存と転倒を
  分ける)。着地点補正と CoP ループ降格はどちらも効かず、後者は有害。
- **§18 の機構は因果が逆だった(§19)。** 着地衝撃も浮上も、傾きが発散した後に
  出る症状。転倒は押した瞬間には決まっておらず、**0.5 s 後の次の歩の荷重移行**
  で決まる。判定量は **CoP が足裏の縁から離れられるか**。
- **ステップタイミング適応は効く(§21)。** 単脚支持の DCM 閉形式を残り時間に
  ついて反転するだけ(除算と対数 1 回、MPC 不要)。生存 232→259/336、13/14 セルで
  改善または同等。ただし発動を DCM 誤差でゲートしないと既定歩容を壊す
  (34/42 → 26/42)。角運動量タスクは**実装前に反証して落とした**(§21.3)。
- **効いたのは幾何だった(§24)。** 足裏を 38 → 46 mm(アンクル筒が既にその幅なので
  掃引体積は増えない)で外乱耐性 +12% と歩容ベンチ +4 ケースが同時に付く。60 mm
  なら +33% / +7 ケース。**制御は 6 手試して 1 手しか効かなかった。** 歩調は
  平均では誤差内で、前後と横で真逆に効く。
- **分離する量は 6 つ見つかり、動かせた 3 つはどれも結果を変えなかった(§22.5)。**
  CoP 飽和・ankle_roll・摩擦・着地衝撃・コミット時の DCM オフセット。**「分離量を
  見つけて動かす」探索は 5 周して 5 回外している。** 相関と操作可能な原因は、
  分離の観察からは区別できない。
- **1 セル 24 点の生存数は ±2 振れる(§20)。** 摩擦係数の 1e-7 相対変化だけで。
  **単一セルの比較で述べた結論は全部誤差の中**で、§19.3 のトルクの件は取り下げた。
  結論は 14 セル合計(336 点)で述べること。その尺度で残るのは、着地点補正が
  **有害**(改善 26 / 悪化 83)、**ステップタイミング適応が有効**(生存 +27 / -1)。
- **残る幾何(立脚幅)は掃引したが、足裏幅のようには勝てなかった(§25)。**
  90/99/110/120/130 mm で歩容ベンチは狭いほど単調に良く、外乱の生存数は
  現行 99 mm が最良、CoP 縁滞在は広いほど改善するがどれも小さい ── 三指標が
  割れ、単純な勝ちが無い。現行値のまま。
- 作業の大半は「動いていたと思っていたものが動いていなかった」の訂正だった。
  §3 の罠一覧を先に読むこと。**特に罠 11 ── 単一の実行結果は測定ではない。**

## 2. 定式化の要点

重心(CoM)を制御する。base の roll/pitch/height を個別に持つ旧版
(`kyo46rs_squat.rs`、比較用に残置)は姿勢タスクと高さタスクが同じ接触権限を
奪い合って頭打ちになる。base の 6 自由度は非駆動なので、バランスに効く唯一の
handle は接触レンチであり、屈伸は「CoM z の指令」でしかない ── 2 つのタスクを
1 つにできる。

タスク段(`levels`):

| 段 | 中身 |
|---|---|
| P0 | EoM + 接触(Baumgarte 付き)+ `patch_contact` + トルク箱 |
| P1 | CoM 加速度(3行) |
| P2 | トランク姿勢、**世界座標**の角ヤコビアン(2行) |
| P3 | 遊脚クリアランス(片足支持時のみ、**z の 1 行のみ**。§4.2) |
| P4 | 姿勢保持(16行、`POST=0` で無効化可) |
| P5 | τ→重力補償 + 接触力→公称配分 の正則化 |

### 触ると壊れるところ

- **接触拘束は Baumgarte 必須。** `zero_contact_acceleration` は
  `J·q̈ + J̇·v = 0`、つまり加速度しか拘束しない。足に角速度が付くと姿勢が
  等速でドリフトし、ソルバは「接触は満たされている」と言い続ける。左右対称な
  屈伸では露見しないが、横移動では**支持足裏が 19° まで転がった**。縁で立てば
  `patch_contact` の矩形 CoP 箱は床に無い領域を記述している。
- **`SOLE_CENTRE_X` / `SOLE_BELOW_FOOT_ORIGIN` / `sole_half_w` は URDF と
  一致必須。** CoP 箱の中心がずれる。片方だけ直すと静かに間違う。
- **armature / joint_damping は WBC 側に手で入れている。** misarta の動力学
  `Model` はロータ慣性を持たない(`armature` は MJCF 出力用フィールドで、
  プラントにしか届かない)。`M` の対角と `h` の速度項に加算している箇所を
  消すと、全駆動関節でモデルとシミュレータが食い違う。
- **`TRUNK_SIGN` は +1(教科書どおり)。** 過去に -1 が必要だった時期があるが、
  あれは misarta の `crba` バグ(§5)の補償であって規約の問題ではない。

## 3. 罠 ── 今日「成果」に見えて artifact だったもの

同じ穴に落ちないための一覧。**いずれも一度は本物だと報告してしまった。**

1. **自己干渉が支えになっていた。** 肩が y=±0.08 のとき前腕が股関節ブロックに
   埋まり、静止姿勢で 16 接触・37.2 kN(体重の 570 倍)が全 tick に存在した。
   片足立ちが「9 秒成立」したのはこれが突っ張り棒だったから。肩を ±0.115 に
   移動して解消。`kyo46rs_com_squat.rs` はスポーン姿勢で非地面接触があれば
   **assert で落ちる**。この assert を消さないこと。
   確認用: `cargo run --features mujoco --example kyo46rs_selfcollision_check`
2. **「SURVIVED」は「ループが total_t に到達した」の意味しかない。** 23° 傾いて
   落下中でも T=8 で切れば SURVIVED になる。T を延ばして再確認すること。
3. **バーンインが偶然に支配されていた。** 位置制御のみの二足は横方向に不安定で、
   その場整定では重心が -0.024〜-0.090 m のどこかに漂着し、生存が運で決まって
   いた。現在は**ベースを固定して関節だけ整定**させ、その姿勢から自由ベースで
   開始する。この分離を戻すと比較が全部コイントスになる。
4. **足幅の閾値はモデルを変えるたびに動いた。** 68→72→90 mm と動き、130 mm で
   逆に転倒(足同士が接触)。足幅は真因ではなかった。
5. **degraded solve のトルクを送ってはいけない。** misa-wbc の HoQp は内側 QP
   失敗時に `x_new = prev.x` を返し、level 0 ではそれが零ベクトル。つまり
   **同次方程式**の解 ── 重力 65 N を丸ごと落とし、接触 Baumgarte 行も一緒に
   捨てる。現在は直前の正常トルクを保持するが、**連続失敗時は開ループになる**
   ので 10 tick 連続で `[OPEN LOOP]` を印字する。この警告が出ている区間の
   数値は制御結果ではない。
6. **`level: 0` は「ハード拘束の衝突」ではない。** 各不等式行が slack を持つので
   常に実行可能。あの status は Clarabel の数値失敗である。ただし
   **「level 0 の degraded が 0 件」を「拘束が満たされている」と読んではいけない**
   ── slack で静かに破った解が `Optimal` として返る。実測で QP 自身の解が
   `fz ≤ f_max` を 21〜68% の tick で破っていた。本文で何度もこの数字を
   「健全の証拠」として使ってしまった。
7. **`Jc` の条件数は脚の特異点を検出できない。** 「片足化で Jc cond が
   32.5→2.1 に改善したから条件数は白」と一度結論したが、`Jc` は浮遊ベースを
   含む 6×nv で、ベースの 6 自由度が空間を自明に張るため脚の特異性は原理的に
   見えない。脚を見るには**脚単体の 6×6**(`kyo46rs_leg_conditioning`)を使う。
   そちらでは膝 63.4° の cond 38.6 に対し 11.3° で 206.3 と実際に悪化していた。
8. **動画の "QP: INFEASIBLE" は長らく `n_stance == 1` を表示していた。**
   ソルバ状態ではなく「片足かどうか」。片足になった瞬間から常時赤くなるので、
   degraded の証拠として読むと必ず間違える。現在は CSV の `degraded` 列
   (実 status)を読む。列が無い CSV では何も表示しない。
9. **ハンドオーバのブレンドは効かない。** フォールバック↔QP の切替段差が
   跳ねの原因だと考えて 10/20/40/80 tick のクロスフェードを試したが全て転倒
   (20 tick で膝が -25.8° まで過伸展)。段差は**制御器間ではなく、QP の壊れた
   解と復帰後の正常解の間**にある ── フォールバックを完全に無効化しても同じ
   離地が起きる。壊れた解に向かってフェードしても意味がない。`BLEND_TICKS`
   は既定 0 で残してある。
10. **偽陽性をまた踏んだ(罠 2 の再発)。** `KP_SWING=100` が T=8 と T=15 で
   SURVIVED を出したので改善と報告しかけたが、T=25 で転倒した。T=15 の時点で
   既に pitch +14.0°、CoM が支持多角形の外(101.9 mm / 限界 89.6 mm)にあった。
   **判定は必ず T=25 以上で行うこと。** 加えて、静的平衡に達したかどうかは
   「T を変えても数値が一致するか」で見る。
11. **§8 修正前は、単一の実行結果が測定になっていなかった。** 実行自体は決定的
   (同条件で degraded が完全一致)だが、**パラメータの 1e-10 相当の変化で
   SURVIVED と FELL が入れ替わった** ── `f_max` を `2.3 × total_mass × G` と
   計算した場合と、同じ値 `149.5856` を直接与えた場合で結果が分かれる。
   本文の掃引で選んだ「最良値」(`HOLD_KP=15`、`ANCHOR_LEAK=0.2`、
   `CTRL_DT=0.002` 等)には、この時点では根拠が無い。原因は §8 の単位混在
   目的関数で、EoM を分離した後は再評価が必要。
12. **フォールバックが姿勢を固めた「成功」に注意。** `f_max` を上げたとき
   G1 が 20 秒立ったが、degraded が全 tick で level 0、CoM が指令から 23.6 mm
   ずれたまま 16 秒間まったく動かず、接触力も 0.1 N まで同一値だった。
   フォールバックの姿勢 PD がシード姿勢で突っ張っていただけ。罠 1 の
   自己干渉と同型で、**「立っている」は「制御されている」ではない。**

## 4. 片足支持: 何が本当の原因だったか

**この節は全面改訂した。初版の「原因は `patch_contact`、ボトルネックは足裏幅」
は誤りである。**

### 4.1 真因 ── 力正則化が均等荷重を要求していた

最下位の力正則化はこう書かれていた。

```rust
forces_nominal[6 * slot + 5] = total_mass * G / nc as f64;   // 両足に均等
```

CoM タスクの零空間では「**足の間で荷重を移す**」と「**CoP を足の外側へ出す**」
が等価である。均等荷重を好む正則化が置かれていると、QP は後者を選び続ける。

静力学で検算すれば必要ないことがすぐ分かる。重心が y=+15 mm、足が ±70.6 mm に
あるなら、両足の CoP を中央に置いたまま荷重を 60.8/39.2 に配れば釣り合う。
ところが実測は:

```
 t     com_y |  fzL   fzR   L%  | copL_y  箱使用率
1.05    15.2 | 32.6  32.5  50.1 |   14.1  0.74     荷重は 50/50 のまま
1.20    20.0 | 33.2  31.8  51.1 |   17.8  0.94
1.35    25.2 | 35.7  29.3  54.9 |   17.9  0.94     以降ずっと飽和
```

**荷重移動を使わず CoP 移動だけで賄っている。** だから 70 mm の横移動のうち
最初の 20 mm で ±19 mm の箱を使い切り、片足遷移を余白ゼロで迎えていた。

正則化の目標を重心指令が示す荷重配分に合わせる(`LAT_SHARE=1`)と:

| | 均等荷重(初版) | 重心整合(修正) |
|---|---|---|
| 移動中の CoP 箱 最大使用率 | **0.99** | **0.17** |
| 荷重配分の追従 | 50%→86%(CoP 飽和後) | 50%→97.9%(重心に追従) |

**CoP 飽和は完全に消える。足裏 98×38 mm は狭くない。**

### 4.2 露出した二層と、その始末

飽和を取り除くと、それが隠していた破綻が順に出てきた。両方とも片付いた。

- **重心の横行き過ぎ。** CoM が立脚足(70.6 mm)を越えて 112.7 mm まで進み、
  支持多角形(〜89.6 mm)の外で倒れていた。`KD_COM` を 40→80 にすると最大
  70.2 mm と解消する。
- **離地直後のロール過渡。** 上を潰しても、遊脚が離れた 100 ms 後に roll が
  −2.5°→−5.7°、200 ms 後に −17.1° へ跳ね、fz が体重の 2 倍に達して倒れていた。

  **持ち上げ動作は原因ではない。** `LIFT_H=0.0`(持ち上げ指令を外し接触だけ
  切る)でも同じく転倒し、peak fz も 206.6 N で完全に一致する。

  原因は遊脚タスクが**世界座標の x,y も硬く拘束していた**こと。目標は
  `swing_home`(初回 tick で凍結した位置)で、胴体を 70 mm 横移動させながら
  遊脚だけ元の場所に留めろという指令になっていた。それを保持する反力が立脚に
  落ちる。このタスクの目的は本来クリアランスだけである。`SWING_ZONLY=1` で
  z 行のみに落とすと解消する。

### 4.3 現状 ── 60 秒の片足立ち

**上の 3 点(荷重配分・CoM 減衰・遊脚 z のみ)を全て入れると片足で立つ。**
2026-07-31 時点でこれが既定。

```
KNEE=1.10 HIP_PITCH=-0.55 ANKLE_PITCH=-0.55 LIFT=1 T=40 \
  cargo run --features mujoco --example kyo46rs_com_squat
```

T=60 まで回した結果:

```
   t    roll°   pitch°    comy     fzL  CoP箱使用率
 6.0    -5.94     0.46   46.58   65.05   0.420
18.0    -8.18    -4.99   46.52   65.04   0.360
36.0    -7.98    -4.94   46.67   65.05   0.379
54.0    -7.81    -3.10   47.82   64.99   0.378
```

roll −5.9〜−8.3°、pitch −5.0〜+0.7°、CoM y 46.5〜49.4 mm、立脚 fz は
65.0 N(体重ちょうど)で一定、遊脚 fz は 0。すべて**有界**で発散しない。
degraded 29 は全て遷移前後に集中し、以後ゼロ。

その後 §4.5 のアンカー修正を入れて、roll −3.58〜−3.90°、最大傾き 0.146 rad、
CoM y 57.0 mm で 60 s 一定まで改善した。以下の表の「現在」はその値。

| 開ループ | 705 ms | 0 | 0 |
| QP と実測の接線力差 | ─ | +22.4 N | **+8.5 N** |
| 検証 | ─ | T=25 静的一致 | **T=60 有界** |

**ただし固定点ではない。** 既定設定は T=15/T=25 で数値が完全一致する静的平衡
だったが、現在の設定は緩やかな変動を続ける有界解である(60 s で roll が
−5.9〜−8.3° の範囲を往復)。倒れないことは確認したが「静止している」とは
書けない。また 7〜8° 傾いた姿勢であって直立ではない。

なお **`UNLOAD_RAMP` は 0 が既定に戻っている。** 荷重配分が正しくなれば
ランプは不要で、むしろ `LAT_SHARE=1` と併用すると CoP 使用率が 1.00 に
戻ってしまう(ランプが荷重目標と衝突する)。

### 4.5 QP の想定接触力と実接触力のずれ

**この節の計測は、他の全ての結論を汚染しうる種類のものである。** crba のバグを
見つけたのと同じ手口 ── 同じ量を独立な 2 系統で測って突き合わせる ── で、
接触力にも系統的なずれが見つかった。

整定した片足姿勢(静止、degraded なし)での実測:

| | fx | fy | fz | \|ft\| |
|---|---|---|---|---|
| QP の想定 | +4.7 | **+23.7** | 71.3 | **24.2 N** |
| MuJoCo 実測 | −0.0 | −0.0 | **65.1** | **0.0 N** |

静止体なので真値は `(0, 0, mg)` 以外あり得ず、65.1 N は体重
(6.64 kg × 9.81)と一致する。**QP は体重の 37% に当たる横力を出している
つもりで、実際には出ていない。** 送っているトルクは存在しない反力を前提に
計算されている。

原因は**接触アンカーの陳腐化**。アンカーは初回 tick で凍結され、その後
立脚足は 11.65 mm 移動する(接触パッチは 24.0 mm)。残った 12 mm の誤差が
`kp_c × 0.0122 = 19.6 m/s²` の横加速度を要求し続け、QP はそれを実現する
横力を計画する。

対処は `ANCHOR_LEAK`(既定 0.2 /s)で、アンカーを足の実位置へ緩やかに追従
させる。**並進のみである。** 回転まで追従させると Baumgarte 本来のドリフト
除去(§2「触ると壊れるところ」、放置すると足裏が 19° 転がる)が死んで全滅する。
`ANCHOR_LEAK_ROT` は既定 0 のまま置いてある。

効果: 接線力差 22.4→8.5 N、法線力差 7.4→2.4 N、整定 roll −7〜−8° → −3.8°、
最大傾き 0.169→0.146 rad。degraded は 28→46 と増える(トレードオフ)。

**残差 8.5 N は消えていない。** QP は依然として体重の 13% の横力を想定して
いる。アンカーだけが原因ではない。

**ゲインは極めて敏感で、動作点が失敗領域に隣接している。**
0.2 生存 / **0.3 転倒** / 0.5 生存 / 2.0 転倒 と非単調。罠 4 と同じパターンで、
モデルを触れば必ず再調整が要る。

#### 摩擦について測ったこと(いずれも直感に反する)

- **滑りと degraded は無関係。** 荷重をかけた状態(fz>20 N)で摩擦錐使用率
  0.6 超の 24 tick のうち degraded は **1 つだけ**。滑りは QP が Optimal を
  返している最中に起きる。「フォールバックが錐を無視している」という見立ては
  誤りだった。
- **地面摩擦を上げると悪化する。** μ 0.7(既定)で生存、1.5 と 3.0 では転倒。
  滑りは単なる欠陥ではなく、遷移のエネルギーを逃がすコンプライアンスとして
  働いている。**現在の成功は足が少し滑ることに部分的に依存している。**
  μ を上げて「綺麗にする」方向へ進まないこと。

### 4.4 次の一手

1. **残差 8.5 N を追う(最優先)。** §4.5 のずれはトルク指令そのものを汚す。
   他のどのチューニングも、この上に載っている限り信用度が落ちる。
2. **遷移時の degraded 46 を消す。** 全て離地前後に集中している。CoP には
   余白があるので、初版のような「箱が足りない」話ではない。
3. **`patch_contact` と足裏幅を疑う作業は不要。** §4.1 で無罪が確定した。
4. **動作実績のあるモデルでの検証を検討中。** kyo46rs は概念モデルで、慣性・
   アクチュエータ配置・可動域のいずれも実機の裏付けがない。今回見つかった
   「狭いゲイン窓」「非単調な閾値」「モデルとプラントの力の不一致」が制御則の
   問題なのかモデルの問題なのかを、この機体だけでは切り分けられない。

## 8. 真因 ── 運動方程式が交渉の対象になっていた

**2026-08-02。この節が現時点で最も重要。**

### 8.1 何が起きていたか

HoQp の各段はこう解かれる。

```
min_{v,w}  ½‖A_k Z v − (b_k − A_k x)‖²  +  ½‖w‖²
```

P0 の `A_0` には**運動方程式**(`M·q̈ − Jᶜᵀf − Sᵀτ + h = 0`、単位 N·m、G1 で 29 行)と
**接触加速度**(Baumgarte 付き、単位 m/s²、12 行)が入り、`w` は摩擦錐・CoP 箱・
`fz ≤ f_max`・トルク箱の slack(単位 N)。

**この三つが重みなしで加算されている。** 単位が通約できないので、どの項が支配
するかは各項がたまたま取る数値の大小で決まる。しかも EoM は `Task::soft_eq` ──
**制約ではなく最小二乗の一項**で、破ることが許されている。

コーンを守るより物理を破る方が残差が小さければ、ソルバはそちらを選ぶ。それが
最小化を指示された内容だから、バグではない。

G1 は質量 5 倍・トルク 10 倍で N·m 行が m/s² 行を圧倒するため、**恒常的に
間違った側**にいた。

### 8.2 対処

HoQp に硬い等式の機能は無いが、カスケードが代わりになる。**EoM を単独で最上段に
置く。** その段には不等式が無いので天秤にかける相手がおらず残差はゼロに落ち、
以降の段は `null(A_eom)` の中でしか動けないので物理が厳密に保たれる。

`EOM_HARD`(既定オン)。

### 8.3 効果

G1、静止、`f_max` は整合性 assert が要求する 770 N(旧構成では全 tick 破綻していた値):

| | 旧 | **新** |
|---|---|---|
| degraded | 165〜667 | **0 / 4000** |
| 最大傾き | 0.35〜0.53 rad | **0.002 rad** |
| CoM 追従誤差 | ─ | **0.87 → 0.21 mm(収束)** |
| 接触力 | 振動 64〜461 N | **167.5 / 167.3 N**(合計 334.8、体重 334.9) |
| QP の解く fz | 上限を 21〜68% の tick で超過 | **最大 166.5 N**(上限 770、超過なし) |

kyo46rs 片足立ち: degraded 33 → **18**、最大傾き 0.140 → **0.045 rad**。
接触・摩擦錐・トランク段の失敗が消え、残るのは姿勢保持段のみ。

### 8.4 これで説明がつくもの

セッションを通じて追った症状は、ほぼ全てこの一点に帰着する。

- QP が自分の摩擦錐を 21〜68% の tick で破る
- level 0 が `NumericalFailure` を出す(`Infeasible` は一度も出ない)
- `f_max` を上げると悪化する
- **1e-10 のパラメータ変化で SURVIVED / FELL が入れ替わる**(§3 罠 11)
- 掃引が軒並み非単調

個別の症状に対して立てた仮説がことごとく外れ続けたのは、すべて症状だったから。

### 9.1 G1 特有だったもの

- **自己干渉。** URDF を素朴に変換すると `pelvis_contour_link` と股関節リンクの
  メッシュが設計上重なり、**片側 241.9 kN**(体重の 722 倍)が全 tick に存在した。
  Unitree 公式 `g1_23dof.xml` はメッシュ geom を全て `contype=0 conaffinity=0` に
  して球 8 個・円柱 4 個だけで接触を取る。同じ方針を `collide_primitives_only` で
  再現した。**代償: 21 リンクが非衝突になり、転倒後の挙動と自己干渉は評価できない。**
- **制御周期。** `mj_substeps` が 0.005 決め打ちだった。G1 は 2 ms が必要(`ctrl_dt`)。
- **足首が足裏の後方 29%** にある(ソール −50〜+120 mm)。kyo46rs 用の屈伸シードだと
  重心が前端まで 10 mm に寄る。hip と ankle に振り分けて中央化する(δ=−0.025)。
- **`f_max` が 150 N ハードコード**で、体重 335 N の半分以下だった。§8 と併せて解消。

### 9.2 残る 1 件 ── 目標がフィードバックで汚染されている

片足は離地までは完璧(degraded 0)で、その 0.2 秒後に崩れる。

```
 t    ns   com_y   ref_y   foot_z    roll°
3.20   1   119.9   126.5   0.03465   +1.07   健全
3.40   1   107.3    88.6   0.03859   −3.38   目標が 37 mm 内側へ飛ぶ
3.85   1    73.0    79.8             −27.25  転倒
```

`y_ref` を**毎 tick 立脚足リンクの現在位置から計算**していた。足リンク原点は
ソールの上にあるので、足首が転がると原点が横に振れ、**重心目標が一緒に振れる**。
実測で足が 4.6 mm 転がり、目標が 2 tick で 37 mm 飛んだ。QP は degraded ゼロで
忠実に追従して倒れる ── **QP は正しく、目標が壊れていた。**

対処: 目標を初回 tick でラッチする(`LATCH_STANCE`、既定オン)。バランス目標は
世界座標の固定点であるべきで、足が動いたらそれは外乱であって新しい目標ではない。

ためのプレースホルダ、`lift_h` は脚長比からの推定。

定式化に効く主要スイッチ:

| 変数 | 既定 | 意味 |
|---|---|---|
| **`EOM_HARD`** | **1** | 運動方程式を単独最上段に置く(§8)。**これが最重要。** 0 で旧構成 |
| **`LATCH_STANCE`** | **1** | 重心の横目標を初回 tick で固定(§9.2)。0 で毎 tick 立脚足から読む旧挙動 |
| `F_MAX_SCALE` | 2.3 | `f_max = scale × total_mass × G`。片足公称(全体重)を下回ると **assert で落ちる** |

| `CTRL_MODE` | torque | `torque` / `hybrid` / `velocity` / `servo`。**torque 以外は全て成績が悪い**(§7 末尾) |

| 変数 | 既定 | 意味 |
|---|---|---|
| `LAT_SHARE` | **1** | 力正則化の荷重目標を重心指令に整合(§4.1)。0 で旧挙動 |
| `UNLOAD_RAMP` | **0** | 遊脚を外す前に力上限を落とす秒数。`LAT_SHARE=1` とは併用しないこと(CoP 使用率が 1.00 に戻る) |
| `SWING_ZONLY` | **1** | 遊脚拘束を z のみに。0 で世界座標 x,y も拘束(§4.2 の転倒要因) |
| `KD_COM` | **80** | CoM 減衰。40 だと横に行き過ぎて支持多角形を外れる |
| `HOLD_KP`/`HOLD_KD` | 15 / 2 | degraded 時フォールバックの姿勢 PD。**狭い**。KP≥20 で転倒 |
| `HOLD_BRIDGE` | 8 | フォールバックへ切り替えるまで凍結で橋渡しする tick 数 |
| `HOLD_LAST` | 0 | 1 で旧挙動(常に直前トルク凍結)。A/B 用 |
| `BLEND_TICKS` | **0** | 切替クロスフェード。効かないことが確認済み(罠 9) |
| `ANCHOR_LEAK` | **0.2** | 接触アンカーが足の実位置へ追従する速さ(1/s)、**並進のみ**。0.3 で転倒する(§4.5) |
| `ANCHOR_LEAK_ROT` | **0** | 同、回転。上げると Baumgarte のドリフト除去が死ぬ |
| `MU_GROUND` | 0.7 | プラント側摩擦。QP の `FRICTION_MU`(0.6)とは別物。上げると転倒する |
| `COPCHK` | 0 | CoP と箱使用率を毎 tick 印字 |

`TRAJ_CSV` には `degraded`(実 status)のほか、足ごとに **CoP・接触力・摩擦錐
使用率・接触パッチの世界位置**を出力する。CoP と接触力は QP の解が含意する値と
MuJoCo の実接触から求めた値の **2 系統**あり(`fqp_*` / `fmj_*`)、これを突き
合わせて §4.5 のずれを見つけた。両者は二重支持中は
1 mm 以内で一致し、**解が壊れたところだけ乖離する**(QP 側が fz=0 に落ちる)。
crba のバグを見つけたのと同じ手口で、片方だけ見ていると必ず騙される。

### 位置/速度制御は試して負けている

`CTRL_MODE` に `hybrid`(位置+速度+τ 前置き、実機の `q,dq,kp,kd,tau` 形式)と
`velocity` / `servo`(速度分解、後者は MuJoCo ネイティブ `<velocity>` +
`implicitfast`)を実装済み。G1 静止 2 ms で測ると:

```
torque                    667 degraded   6.63 s   ← §8 修正前の比較
hybrid   kp=60  kv=8      553            1.79 s
velocity kv=20            205            0.46 s
servo    kv=10000          64            0.22 s
```

硬くするほど悪い。速度サーボは接触レンチを QP から取り上げるので、QP が
「この力配分で CoM を動かす」と計画している間にサーボが関節速度を決めてしまう。
なお `kv < 2I/dt` の上限は **MuJoCo の制約ではなく** articara が Rust 側で
陽的 PD を計算して `<motor>` に流していたことの制約で、ネイティブサーボでは
kv=10000 まで発散しない。

動画は `examples/render_com_squat_video.py <traj.csv> <out.mp4>`。
`ROBOT=g1` でメッシュ機体に対応(全 STL を読み、画面 1px 未満の面のみ間引く)。URDF の
プリミティブを numpy + PIL で自前ラスタライズする(mujoco の Python
バインディングは使わない)。メイン視点に加えて**正面図**と**足裏を上から見た
CoP パネル**(箱の枠・QP 想定・MuJoCo 実測・軌跡)を右列に出す ── 横方向の
体重移動はメインカメラでは真横から見えないため。`COMPACT=1 VID_W=640` で
並列比較用の狭いフレーム、`ANKLE_CLOSEUP=1` で足首の寄り。

### プラント側の制約

- **`SIM_DT = 1 ms` は必須。** `MujocoSim` の関節 PD は陽的な速度帰還で、
  `actuator_kv < 2·I/dt` でしか安定しない。遠位のロール関節は
  `I ≈ 6e-4 kg·m²` なので 2 ms では `kv` 上限が 0.63 ── 位置保持に使いたい値を
  下回る。実測(`kyo46rs_stand_check`、WBC 無し): 2 ms は t=0.65 で崩壊、
  1 ms / 0.5 ms / 0.25 ms は同一パラメータで 5 秒立つ。

### 10.2 DCM 基準を増大指数で評価してはいけない

`xi = c + c_dot/omega` は `xi_dot = omega (xi - p)`、**固有値 +omega の発散系**。
初版は各セグメントの始端値から `exp(+omega t)` で前進評価していた。後ろ向き
再帰が係数を `exp(-omega T)` 倍しているので、`xi_ini - p0 - v/omega` は桁落ちの
塊であり、そこへ `exp(+omega T)` を掛ける。

最終の両足支持セグメントが 10 秒、omega=5.585 のとき `exp(55.9)=1.8e24`。真値
~1e-26 の係数が倍精度の丸め ~9e-18 になり、**基準 DCM が -0.39 m** に飛んだ ──
計画 ZMP が ±0.042 m しか動かない軌道に対して。ロボットは忠実に追従して倒れた。

対処: セグメント**末端**から `exp(-omega (T - t))` で評価する(同じ解の別表現、
指数が減衰側)。`a_long_trailing_segment_does_not_blow_the_reference_up` で回帰。

**同じ理由で、DCM 基準を前進オイラー積分で検証してはいけない。** 最初に書いた
検証テストがそれで、正しい実装に対して落ちた。点ごとの ODE 残差で見ること。

### 10.9 kyo46rs2 は干渉を緩和しない(実測)

  torso ixx ×1.94 / iyy ×1.53、前腕 ixx ×0.72、各リンクに 0.1〜1 mm の重心オフセット

したがって **§10.4 の前腕⇔股関節は v2 でもそのまま**。実測:

| | v1 | v2 |
|---|---|---|
| 片足立ち T=60 自己干渉 | 11620 tick / 37.1 N | **11700 tick / 38.2 N** |
| 片足立ち degraded / 傾き | 21 / 0.046 rad | **11 / 0.044 rad** |

### 10.10 解決済み ── 「再コンパイルでずれた」は別セッションの編集だった

§10.1 の「抽出前後でバイト単位一致」は**その時点のバイナリでは成立していた**
(2026-08-02 11:08、stand / squat / oneleg の 3 本)。その後 §10.4 以降の診断を
足していく過程で、**同じコマンドの出力が基準 CSV と一致しなくなった。**

わかっていること:

- **実行は決定的**。同一バイナリで 3 回回して CSV が完全一致する
- 原因は `KYO46RS2` の追加ではない(外しても同じ)、毎 tick の自己干渉カウンタでも
  ない(外しても同じ)、`codegen-units` でもない(1 と既定で同一)
- ずれは **tick 0 から**始まり、特徴的な署名がある ──
  **`acc_ref_z`(立脚足の Baumgarte 垂直加速度指令)がちょうど 1/2 になる。**
  stand で -1.0021 → -0.5010、oneleg で -1.2478 → -0.6239。
  tick 0 ではアンカー誤差がゼロなので `acc_ref[5] = -kd_c * vel[5]`、つまり
  **足の垂直速度が半分になっている**(0.0125 → 0.0063 m/s)
- 定性的な結論は変わらない: stand / squat / oneleg はいずれも SURVIVED、
  片足立ちの最大傾き 0.045 → 0.046 rad、degraded 43 → 21

**原因が判明した。作業ツリーを共有する別セッションの編集である。**
G1 の片足立ちを追っていた側が 11:33 に `6ba64d2`
(`fix(wbc): the contact stabiliser was tuned for two feet and slammed one`)を
コミットしており、その中で `KD_CONTACT` の既定が **80 → 2·sqrt(400) = 40**
に変わっていた。tick 0 はアンカー誤差ゼロなので
`acc_ref[5] = -kd_c * vel[5]` ── **ちょうど 1/2 になる**。署名がそのまま
説明される。私のバイト一致確認は 11:08、彼らのコミットは 11:33 だった。

回帰ではない。ただし**教訓は残る**:

- **同じ作業ツリーで 2 つのセッションが動いている。** ソースが自分の知らない
  うちに変わる前提で測ること。「同一バイナリでのみ比較可能」は結論として
  正しかったが、理由は浮動小数点ではなくこれだった。
- 同じコミットは私の `src/biped/` 抽出も巻き込んでいる(1894 行の変更)。
  履歴上、example の抽出は `6ba64d2`、モジュール本体は `c6dd5ef` にある。

`csv/baseline2/` は現行バイナリ(kp_c=400 / kd_c=40)の基準として有効。

### 10.11 真の壁は hip_roll の**トルク**、そして立脚幅がその両方を決める

§10.4 で腕を疑い、§10.5 で ankle_roll の可動域を疑ったが、**どちらも本命では
なかった。** 崩れる直前のトルク需要を関節ごとに効力限界比で見ると一目でわかる
(腕を y=0.130 へ逃がして自己干渉ゼロにした状態、W1):

```
 t=1.800   L_hip_roll  76%      ← 他は ankle_roll 2%, knee 10%
 t=1.830   L_hip_roll 100%      ← ここから接触力が暴れ出す
 t=2.025   全関節 100% 超       ← 転倒
```

検算が合う。片足支持で立脚側 hip_roll が支えるのは
「上体 4.2 kg × 0.07 m + 遊脚 1.2 kg × 0.14 m ≒ 4.5 N·m」で、実測 4.56 N·m。

**EL05 の連続定格 1.8 N·m の 253%、ピーク 6.0 N·m の 76%。**
§6 が「支持脚の hip_pitch だけは片足支持が必要で未測定」と残していた宿題の、
hip_**roll** 版の答えである。

#### 可動域を広げても直らない(反証済み)

肩 y=0.130 + ankle_roll/hip_roll を ±20/25/30/35° に広げた 4 条件は、
**すべて 2.08 s 前後で同一に転倒する。** 限界に当たっていたのではなく、
限界に届く前にトルクが尽きていた。

#### モーメントアーム = 立脚幅。だから一箇所で両方が直る

hip_roll のモーメントアームは立脚幅そのもの。そして立脚幅を狭めると
**股関節ブロックが内側へ寄るので、前腕との干渉も同時に消える。**
`left_hip_yaw_joint` の origin y を動かすだけ:

| hip_y | 立脚幅 | 自己干渉 tick | degraded | DCM 誤差 | ankle_roll |
|---|---|---|---|---|---|
| **0.070**(現行) | 139.6 mm | **4649**(ピーク 89.9 N) | 0 | 12.8 mm | 79% |
| 0.055 | 109.6 mm | **0** | 0 | 5.6 mm | 69% |
| 0.045 | 90.0 mm | **0** | 0 | 4.9 mm | 58% |

肩は 0.115 のままでよい。前腕の内側面 0.0975 に対し、股関節ブロックの回転時
最外 y は 0.045+0.0354 = 0.0804 ── 余裕 17 mm。

なお**肩だけ外へ出す**(y=0.125〜0.140)と自己干渉は消えるが、次に hip_roll の
トルク壁が来るので 2.0 s で転倒する。順序として立脚幅が先。

#### それでも足踏みは 3〜4 歩

`hip_y=0.045` で、**片足支持そのものは非常に健全**:
立脚 hip_roll 53〜56%、他の関節は 15% 以下、傾き 0.002 rad、degraded 0。

残るのは**両足支持の遷移**で、そこだけ **両脚の hip_roll が同時に 91〜98%**
へ跳ねる(t=2.540 で 98%/94%、2.620 で 91%/92%)。両脚が地面を介して閉ループを
作ったときの内力である。`T_DS` 0.20/0.30/0.45、`T_SS` 0.45/0.60、`K_DCM` 2/3、
`LOAD_RAMP_FRAC` 0.6/0.9 はいずれも効かない ── 時間の問題ではない。

#### 推奨(測定に基づく順序)

1. **`hip_yaw_joint` の origin y を 0.070 → 0.050 前後に。** 数値ひとつで
   前腕干渉と片足支持 hip_roll トルクの両方が解ける。新しい自由度は不要で、
   腰関節も腕の P/R/P も要らない ── 壁は運動学ではなくトルクだった。
2. 立脚幅を広く保ちたいなら、代わりに **hip_roll を 2 基**にする(膝と同じ扱い)。
   4.56 N·m は EL05 1 基の連続定格の 253%。
3. 次の作業対象は**両足支持の内力**。P5 の力正則化は各足の fz しか指定して
   おらず、両脚を突っ張らせる内力成分は零目標のまま放置されている。

## 11. 足踏み ── 動くようになった経緯(2026-08-02)

**3 歩 → 25 歩。** 立脚幅の変更を出荷 URDF に適用し(§10.11)、その上で効いたのは
**G1 側で見つかった Baumgarte ゲインの知見**と、私が walk ドライバに作り込んだ
バグ 4 件の修正である。

### 11.1 立脚幅を出荷モデルに適用

`kyo46rs_description/urdf/kyo46rs.urdf`、`hip_yaw_joint` の origin y を
**±0.07 → ±0.05**(立脚幅 139.6 → 99.4 mm)。関節原点 2 + 出力側マーカ 2 の

効果: 前腕⇔股関節の自己干渉が消え(4649 tick → 0)、片足支持の hip_roll

G1 の片足立ちで得られた知見「両足用のゲインが片足を弾いていた」がそのまま
当てはまった。`KP_CONTACT` を振ると(`KD_CONTACT = 2*sqrt(KP_CONTACT)`、T=40 /
N_STEPS=40、実歩数):

| `kp_c` | 60 | 100 | 120 | **150** | 180 | 220 | 250 | 400 | 600 | 1600 |
|---|---|---|---|---|---|---|---|---|---|---|
| 歩数 | 9 | 16 | 17 | **25** | 10 | 13 | 17 | 9 | 6 | **3** |

**`kd_c=24` で 25 歩、`kd_c=2·sqrt(150)=24.495` で 18 歩。**
減衰を 2% 動かすと 7 歩変わる。§3 罠 11 と同じ形で、ここのどの数値も単独では
結果ではない。**堅い言い方は「1600 は 3 歩、60〜250 のどこでも 9〜25 歩」**。

既定は原理的なペア(`kp_c=150`, `kd_c=2·sqrt(kp_c)`)にしてある。
**再現する数値は 18 歩**であって 25 ではない。

### 11.3 walk ドライバにあったバグ 4 件

いずれも「接触集合と現実がずれる」系。順に潰した。

1. **接触補正が足を永久に排除していた。** 分岐をスケジュールで切っていたため、
   遊脚期間で `off_count` が飽和した足が両足支持相に入った瞬間に落とされ、
   再投入の経路は `!sched` 側にしか無かった。判定は**測定状態のヒステリシス**で
   行い、スケジュールは初期条件としてのみ使う。
2. **接触集合にも遊脚タスクにも属さない足は直交空間で無拘束。** 弱い姿勢保持
   段しか効かないので、QP は空いた脚を重心制御の反作用質量として使う ──
   実測、着地したばかりの足が **80 mm まで放り上げられ**、1 秒間そこに留まった
   まま反対脚で転倒した。**接触外の足には必ず Cartesian タスクを与える。**
   「スケジュールが両足支持だから」はタスクではない。
3. **着地アンカーを空中に置いていた。** admit した tick の実測姿勢をそのまま
   アンカーにしていたが、跳ねている着地はまさに床から 3〜5 mm 浮いた状態。
   Baumgarte が kp_c=1600 でそこに**保持しようと**し、存在しない反力を計画する。

4. **補正が計画された離地を拒否権付きで上書きしていた。** 予定遊脚の足が

   永遠に上がらない。**20 歩「成功」の正体は頂点 0.2〜1.2 mm の擦り足だった。**
   補正の役目は「予期しない接地の追加」と「失われた接地の削除」だけ。

## 12. yaw ── 動画で見えた捻れと、腰関節を足すかどうか(2026-08-02)

### 12.1 足先の yaw が動いていた

動画を見た指摘から。実測すると、16 歩で

```
hip_yaw   0.04° → ±30°   ← 可動域の端に張り付き
足先 yaw  着地時に最大 31°  ← 角で着地している
ベース yaw ±8°
```

**穴が 2 つあり、両方塞いで初めて直る。**

1. **遊脚タスクが並進 3 行だけだった。** 回転 3 自由度は弱い姿勢保持しか
   効かず、QP が空いた脚の yaw を零空間の捨て場に使う。接触外の足を無拘束に
   していた §11.3-2 と同型で、脚が捻れるだけなので見つけにくい。
2. **スタック全体に yaw の制御が無かった。** トランクタスクは roll/pitch の
   2 行のみ。捻れが入れる鉛直軸まわりの角運動量を誰も受け止めていない。

| | 歩数(T=40) | DCM 誤差 |
|---|---|---|
| どちらも無し | 18 | 637 mm |
| トランク yaw のみ | 28 | 19.1 mm |
| 遊脚 yaw のみ | 31 | 337 mm |
| **両方** | **40(完走)** | **10.3 mm** |

**姿勢は全部拘束してはいけない。** 最初に遊脚を 6 行(位置+姿勢)にしたら
**何もしないより大幅に悪化**した ── ゲイン 25/60/150/400 のすべてで 1〜2 歩。
立脚接触が既に 6 行、CoM + トランクで 5 行を使っているので、遊脚に 6 行を
足すと脚の零空間が消える。`SwingAxes::XyzYaw`(4 行)が正解。

### 12.2 これで周期解になった

| horizon | 歩数 | DCM 誤差 | ankle_roll | degraded |
|---|---|---|---|---|
| T=40 | 40 | 10.3 mm | 102% | 24 |
| T=60 | 80 | 12.7 mm | 104% | 35 |
| **T=110** | **150** | **8.8 mm** | 102% | 61 |

horizon を伸ばしても劣化しない ── むしろ 150 歩の方が誤差が小さい。§11.4 の
「T を伸ばすと落ちる」偽陽性とは質が違う。yaw 修正後の実測で
hip_yaw 最大 1.6°/4.1°、ベース yaw 最大 0.19°、CoP 箱使用率 1.00 → 0.54、
自己干渉 0。

### 12.3 腰関節を足すとどうか(実測)

`torso` を pelvis(脚)と上体(腕・頭)に割り、間に関節を入れた変種で比較
(`scripts/kyo46rs_variants.py --waist`、T=60 / N_STEPS=80):

| 腰の自由度 | 歩数 | DCM 誤差 | degraded |
|---|---|---|---|
| **無し(現行)** | **80 完走** | 12.7 mm | 35 |
| **yaw** | **80 完走** | **10.2 mm** | 93 |
| roll | 1 | 280 mm | 22 |
| pitch | 8 | 363 mm | 86 |
| yaw + roll | 5 | 182 mm | 43 |
| yaw + pitch | 28 | 296 mm | 446 |
| yaw + roll + pitch | 4 | 113 mm | 42 |

**yaw だけが中立〜わずかに有利で、roll と pitch を含むと全て悪化する。**

読み方に 2 つ注意がいる。

- **比較は腰に有利な側へ倒してある。** 質量は高さ按分の一様分布で割って
  いる(実際の torso は重心が 21 mm 下寄りで下重心)し、腰に乗るはずの
  アクチュエータ質量(EL05 1 基 0.242 kg)を足していない。それでも
  roll/pitch は負ける。
- **roll/pitch 用のタスクを書いていない。** 現状のトランクタスクは上体の
  roll/pitch を規制し、CoM タスクは全体に効く ── 腰はその間の柔らかい継手に
  なる。「pitch は駄目」ではなく「**今の制御則では駄目**」が正しい。腰 pitch を
  使う設計なら、骨盤が傾いても上体を立てるタスクを併せて書く必要がある。

**結論: 指摘された yaw の問題は制御側で解けており、腰関節は要らない。**
腰 yaw は追従を 12.7 → 10.2 mm に改善するが、アクチュエータ 1 基と
degraded 35 → 93 の代償に見合うかは別の判断。

## 13. 前進歩行(2026-08-02)

### 13.1 構造変更は一箇所

`Footsteps`(初期に採った 2 点の固定ペア)を `FootstepPlan`(スライスごとの列)
にした。これを読んでいるのは 5 箇所 ── ZMP 計画、遊脚の着地目標、指令 ZMP を
クランプする支持多角形、荷重配分、着地アンカーの z。**`stride=0` が足踏みを
そのまま再現する**ので、動く歩容が別経路に分岐しない。

`stride` は**胴体の 1 歩あたり前進量**。遊脚はその 2 倍動いて立脚足の 1 歩先に
着く。ここを取り違えると「安定して歩いているのに速度が指令の半分」になる。

### 13.2 持続速度 0.091 m/s

`T_SS=0.35`、`STRIDE_RAMP=6`、200 歩 / 115 s:

| stride | 速度 | 走破 | |
|---|---|---|---|
| 0.02 | 0.036 m/s | 3.95 m | 100% |
| 0.03 | 0.055 | 5.92 m | 100% |
| 0.04 | 0.073 | 7.89 m | 100% |
| **0.05** | **0.091** | **9.87 m** | **100%** |
| 0.06 | 0.109 | 3.86 m | **66 歩で転倒** |

**走破率を必ず見ること。** 転倒しない歩容が計画の 55% しか進んでいない、は
普通に起きる。

### 13.3 歩き出しが律速だった

stride 0.06 以上の転倒はすべて **1 歩目の 1.0〜1.7 秒後**に集中し、蓄積の形を
していなかった。立ち止まった状態にいきなり全長の一歩を要求しており、片足支持に
入った瞬間から DCM が歩行速度で動いていなければならない。数歩かけて stride を
立ち上げる(`STRIDE_RAMP`、既定 6)と 0.06 が 3 歩 → 60 歩に伸びた。

`STRIDE_RAMP` も非単調(0.06 で ramp 6 は 60 歩、ramp 15 は 34 歩)。

### 13.4 外した仮説(記録)

- **omega·T_ss が大きすぎる説。** 片足支持中 `e^{omega T}` で誤差が増幅されるのは
  事実(2.51 → 12.3 倍)だが、`T_SS` を 0.45→0.35→0.28→0.22 と縮めても
  stride の上限は 0.04〜0.05 のまま。0.35 が最良で、それ以下は悪化する。
- **前後方向の CoP 箱が上限を決めている説。** 転倒直前に `zmp_cmd_x` が箱の
  前端 0.1634 でクランプされ CoP 使用率 1.00 になるのは事実。しかし
  `ZMP_MARGIN` を 1.0 にしても `SOLE_HALF_L` を 0.049→0.120 にしても
  3〜4 歩のまま変わらない。**クランプは症状。**
  (なお `SOLE_HALF_L` は QP の箱だけを広げて実際の足裏は変えないので、
   あの掃引は物理検証としては無効。§2 の「URDF と一致必須」に該当する。)

### 13.5 次(この推奨は §13.7 で外れた)

**指令 ZMP が支持多角形を出るときにクランプするのではなく、着地点を動かす**
(capture point / Raibert)のが定石で、ここが次の構造。現在のクランプは ξ が
箱を越えた瞬間に補正の符号を反転させる ── §11 で横方向に見たのと同じ機構が、
前後方向で再現している。

**→ 実装して測ったところ効かなかった。§13.7 を参照。**

### 13.6 歩容が左右非対称だった(指摘、修正、そして効かなかった)

`constant_stride` は毎回の遊脚を「今いる場所から 2×stride 前」に置いていた。
一見正しいが、両足が揃った状態から始めると

```
1 歩目(右)  L 0.000  R 0.100   右が先行
2 歩目(左)  L 0.100  R 0.100   ← 揃う
3 歩目(右)  L 0.100  R 0.200   右が先行
```

**右足が常に先行し、左足は追いつくだけ**の「出して揃える」歩容になる。
1 歩おきに前後の足間隔がゼロになり、その両足支持は前後方向の支持余裕を
持たない。

直し方は 1 歩目だけ。**最初を半歩**にすると位相が合い、以降は毎回 2×stride で
先行足が交替する(最後も半歩で閉じ、DCM 計画の「中央で静止して終わる」終端
条件と噛み合う)。`FootstepPlan::alternating`、既定オン。単体テストで
「定常歩は必ず 1 stride 離れ、先行が毎歩入れ替わる」を検証している。

**ただし安定性は改善しない。** stride 0.05(持続速度)では両者とも 200 歩
完走で同等、stride 0.06 では **66 歩 → 26 歩と悪化**する。

さらに、**1 歩ごとの動力学はもともとほぼ対称だった**:

| | fz_peak L / R | 遊脚頂点 L / R | 着地 vz L / R |
|---|---|---|---|
| 出して揃える | 77.5 / 77.3 N (−0.2%) | 22.3 / 22.3 mm | −0.082 / −0.082 |
| 交替(修正後) | 77.3 / 78.3 N (+1.2%) | 22.5 / 22.3 mm | −0.081 / −0.083 |

どちらの足も毎回 2×stride を振っているので、非対称なのは**足跡の幾何**で
あって 1 歩あたりの荷重ではなかった。幾何の対称性は歩容として正しく、実機の
摩耗や見た目にも効くが、**速度を縛っていたものではない**。

### 13.7 capture point を試した ── クランプは症状だった

§13.5 の推奨を 2 通り実装し、どちらも効かなかった。

**1. 着地時 DCM の開ループ予測で着地点をずらす(教科書形)。** 全域で悪化する。
持続速度 0.05 で 200 → 190 歩、0.06 で 26 → 14 歩、補正量は最大 65 mm。

理由は定式化の誤りで、**ZMP フィードバックと二重に補正していた**。予測は
「ZMP が計画通りなら」の開ループだが、実際にはフィードバックが ξ を基準へ
引き戻している。片足支持の頭では `e^{omega*0.35} = 7.0` 倍されるので、
5 mm の追従誤差が 35 mm の着地点移動になる。

**2. ZMP の飽和量だけ着地点をずらす。** 足が動くべきなのは「ZMP が仕事を
できない」ときだけ、という筋でトリガをクランプ不足量 `p_raw - p_cmd` に変更。

| stride | クランプのみ | capture point | 補正回数 |
|---|---|---|---|
| 0.05 | 200 歩 | 200 歩(同一) | **0 回** |
| 0.06 | 26 歩 | 26 歩 | 1 回 / 67 mm |
| 0.08 | 8 歩 | 8 歩 | 1 回 / 16 mm |
| 0.10 | 7 歩 | 7 歩 | 1 回 / 56 mm |

**持続速度では 1 度も発火しない。** その上の速度では**崩れる瞬間に 1 回だけ**
発火し、そのときには 67 mm の補正でも手遅れ。

つまり **ZMP クランプは症状であって原因ではない。** §13.5 の見立ては誤りだった。
既定は OFF(`ADAPT_STEP`)、機構自体は正しいので残してある。

### 13.8 stride 0.06 の壁 ── 現時点で外した仮説

| 仮説 | 検証 | 結果 |
|---|---|---|
| omega·T_ss が大きすぎる | T_SS 0.45/0.35/0.28/0.22 | ✗ 上限は 0.04〜0.05 のまま |
| 前後 CoP 箱が狭い | ZMP_MARGIN 1.0、SOLE_HALF_L 0.12 | ✗ 3〜4 歩のまま |
| 歩容が左右非対称 | 交替式に修正 | ✗ 同等、0.06 では悪化 |
| ZMP クランプが符号反転を起こす | capture point 2 通り | ✗ 持続速度では未発火 |
| 歩き出しが急 | STRIDE_RAMP | ○ **これは効いた**(3 → 60 歩) |

0.06 の転倒は 26 歩・t=16.1 と、健全に歩いた後に来る ── 0.05 には無い蓄積が
0.06 にはある。**次はその蓄積量を歩ごとに測ることから。** §11 で着地速度の
蓄積を見つけたときと同じ手口が要る。

## 14. 文献に沿って 2 つ試した(2026-08-02)

一次資料で検証した上で、推奨順に 1 つずつ試した記録。

### 14.1 stride 0.05 は 1000 歩・49.85 m 走破する

200 歩しか回していなかったので、`|lambda| = 1.02` なら 200 歩で 52 倍にしかならず
偽陽性かもしれない、という指摘を受けて検証した。結果は **1000 歩・49.853 m を
計画どおり 100% 走破**。転倒は t=568 で、歩行区間は 552 s に終わっているので
**歩き終えて 16 秒後の整定過渡**である。§10.10 で見たものと同じ。
歩容そのものは持続する。**歩行停止後に倒れるバグは別に実在する。**

### 14.2 接触駆動の相遷移 ── 前提が間違っていた

「予定時刻ではなく接地で相を切る」を実装(`PHASE_BY_CONTACT`、`GaitPlan::retime` +
DCM 計画の再構築)。

**素朴なトリガは壊滅的だった。** 「体重の 10% 以上の荷重で歩を終える」は
**遊脚が途中で床を擦っただけで発火**し、45 回の発火で合計 2740 ms ──
350 ms の歩から毎回 61 ms(17%)を切り落として、200 歩 → 46 歩になった。
遊脚の後半(`PHASE_MIN_FRAC=0.75`)でしか着地を認めず、荷重 30%・3 tick 継続を
要求して解消。

直した上での結果:

| stride | 時刻ベース | 接触駆動 |
|---|---|---|
| 0.05 | 200 歩 | 200 歩(DCM 誤差 12.2 → 11.1 mm) |
| 0.06 | 26 歩 | **16 歩** |

**そして前提が外れていた。** 私は「遊脚が 30 ms 早く着地する」を根拠にこれを
最優先に置いたが、その測定は**足踏み時の別設定**のものだった。現在の歩行では
発火は**ほぼ全部「遅い着地」**(45 回、平均 5 ms)で、早い着地ではない。
既定 OFF。

### 14.3 CoP ループを降格し、着地点に主役を渡す ── これは効いた

小足のロボットは CoM/CoP ではなく**着地点で釣り合わせる**、というのが文献の
一貫した指針(Kim et al. 2019 arXiv:1901.08100 「これらの制御器は
**at no point attempt to directly control the CoM instantaneous state**」;
Khadiv et al. 2016 arXiv:1609.09822 は受動足首機がステップ調整**だけ**で安定
したと報告)。我々の横方向 CoP 箱は ±19 mm しかないのに `k_dcm=2` の CoM/CoP
ループに主役をやらせ、ステップ調整は既定 OFF だった ── 指針と逆向き。

stride 0.06(壁)で:

| | adapt OFF | adapt ON |
|---|---|---|
| k_dcm=2.0(現行既定) | 26 歩 | 26 歩 |
| k_dcm=1.0 | 30 歩 | **77 歩** |
| k_dcm=0.5 | 24 歩 | **92 歩** |

**着地点補正は CoP ループを降格して初めて効く。** k_dcm=2.0 では adapt を
入れても 26 歩のまま動かない。§13.7 で「capture point は効かない」と結論した
のは、**k_dcm=2.0 のまま試していたから**である。2 つのループが同じ誤差を
取り合っていた、という文献の指摘がそのまま当たっていた。

**ただし速度上限は上がらない。** k_dcm=0.5 + adapt を速度域に持ち上げると
0.05 は 200 歩(100%)、0.06 は 92 歩(46%)、0.07 と 0.08 は 8 歩。
持続速度は 0.05 のまま。そして k_dcm も例によって非単調
(0.25→12、0.35→36、**0.50→92**、0.75→64)なので、0.5 という値自体に
根拠は無い。

既定は変えていない(k_dcm=2.0、adapt OFF)。運転点 0.05 では k_dcm=0.5 だと
degraded が 7206 に増える(2.0 なら 559)ので、どちらも一方的には勝たない。

### 14.4 歩き終えると倒れるバグ ── 尻尾が計画を間延びさせていた

§10.10 / §14.1 で 3 回別々の設定で再現していたもの。短い歩行 + 長い整定で
再現させると一目だった:

```
   t  sup ns    com_y    err   fzL    fzR
 8.00   0  1  -0.0477 0.0010   1.0   64.1   ← 歩行終了直後
12.00   0  1  -0.0406 0.0005   0.6   64.4
16.00   0  1  -0.0333 0.0003   0.6   64.5
19.00   0  1  -0.0277 0.0003   0.7   64.3
19.50   0  2  -0.0471 0.0467  18.3   37.5   ← 左足がついに荷重を拾う
20.00   ─  ─  -0.2571 0.3762   0.0    0.0   ← 転倒
```

**歩き終えたあと 11 秒間、片足で立っていた。** 重心 y が 2 mm/s で中央へ
戻り、遊脚側がようやく 18 N を拾った瞬間に倒される。DCM 誤差は直前まで
0.0003 で、傾きも 0.001 ── 指標は最後まで健全に見える。

原因は `GaitPlan::new` が**最終の両足支持スライスを `t_end` まで引き伸ばして
いた**こと。DS の ZMP は「最後の立脚ソール → 中央」を線形にランプするので、
25 秒の尻尾なら**「中央で静止して終わる」に 25 秒かける**。

修正は 2 点:

1. 整定を**独立したスライス**にする(最後の歩間 DS は `t_ds` のまま)。
2. DS の ZMP 始点を「直前セグメントの終端」にする。歩の間では従来と同一値に
   なるので歩行中の挙動は不変で、尻尾でだけ効く ── 後ろ向きに単一支持を
   探す実装だと、尻尾のスライスが何枚あっても毎回「最後の立脚ソールから」
   ランプし直してしまう。

効果:

| | 修正前 | 修正後 |
|---|---|---|
| 10 歩 + 25 s 整定 | t=20.0 転倒 | **SURVIVED** |
| 足踏み 20 歩 + 尻尾 | t≈57 転倒 | **SURVIVED** |
| 200 歩 | SURVIVED / 誤差 12.2 mm | SURVIVED / **6.9 mm** |
| **1000 歩 + 整定** | t=568 転倒 | **SURVIVED / 49.844 m / 100%** |

**これまで報告してきた DCM 誤差の最大値は、ほぼ全部この過渡だった。**
§13.2 の 12.7 mm も §11 の 72 mm も同じ。歩行中の実力は 6.9 mm。
`ankle_roll` も 104% → **69%**、自己干渉 0、`[OPEN LOOP]` 0。

### 14.5 ③ DCM 計画の連続再構築 ── 効いた。ただし ①②④ を直した後で

補正を**計画に入れる**(足を動かした瞬間に DCM 基準を作り直す)形にした。
従来は着地時にしか再構築しておらず、遊脚中は `xi_ref` が元の足位置を

## 15. 全身ベンチマーク(2026-08-02)

### 15.1 指令を速度に一般化した

`FootstepPlan::velocity(vx, vy, wz)`。**足位置は、毎歩 `(vx,vy)*T` 進み
`wz*T` 回る「体幹フレーム」に固定したオフセット**として置く。歩 k で振る足は
歩 k+1 の体幹位置に着くので、体幹は 1 歩あたり 1 stride、足は 2 stride 動く ──
これが交替歩容そのもので、x のみ版で必要だった「1 歩目を半歩」の補正が
**構成から自動的に出る**。前後・横・旋回が同じ式で書ける。

足が交差しないことも構成から出る: 2 つのオフセットは体幹フレームに固定なので、
フレームがどう動いても左右が入れ替わらない。単体テストで検証
(`velocity_command_reproduces_the_x_only_plan` は x のみ計画との厳密一致、
`sideways_and_turning_keep_the_feet_on_their_own_sides` は交差なし、
`turning_rotates_the_footstep_yaw` は足の向きが body と一緒に回ること)。

`Footsteps` に **yaw** を持たせ、遊脚の姿勢目標がそれを追う。これが無いと
旋回時に体幹だけ回って足は世界に対して真っ直ぐのまま着地する。

屈伸は重心高さの変調(`SQUAT_AMP` / `SQUAT_PERIOD`)。**omega は公称高さのまま**
にしてある ── LIPM は一定高さで導出されており、毎 tick 引き直すのは可変高さ
DCM という別の定式化になる。したがって屈伸は水平ループにとっての外乱で、
ベンチに入れる意味はそこにある。

### 15.2 ハーネス

`scripts/kyo46rs_bench.py`。36 ケース、5 分。全ケースで歩数を揃えてある。

**要は achieved 列であって survived 列ではない。** 転ばないまま指令の 55% しか
進まない歩容はこのロボットで実際に起きるし、見た目は歩行と区別がつかない。
判定は「生存」かつ「指令した全軸で 85% 以上追従」。

## 16. 旋回 ── 座標系の取り違えと、指標のほうのバグ(2026-08-03)

§15 で「旋回は全滅、0.05 rad/s でも転ぶ」と書いた。**そのうち転倒のほうは
実装バグ、"0.1 rad/s で頭打ち" のほうは指標バグだった。** 修正後、0.05〜0.80
rad/s のすべてで指令の 100% を追従して生存する。

### 16.1 転倒の真因 ── 姿勢誤差を世界座標の行に直接入れていた

`trunk_rp_ref` は ZYX オイラー角の roll / pitch 誤差を、体幹タスクの
**世界角加速度行 (wx, wy) にそのまま**書き込んでいた。ヨー 0° なら一致するが、
90° 回れば機体のロール軸は世界 +y を向くので指令が別の軸に出る。90° を越えると
符号まで反転する。

診断で決まった。**転倒が「一定時間後」ではなく「一定の累積ヨー角後」に起きる**:

| 指令 wz | 追従率 | 転倒時刻 | 転倒までの累積ヨー |
|---|---|---|---|
| 0.10 | 93% | 22.58 s | 約 120° |
| 0.20 | 91% | 14.18 s | 約 104° |
| 0.40 | 89% | 9.75 s | 約 90° |

レートは達成できていて、時刻でも角速度でもなく**回った角度**で壊れる。
90〜120° に集中するのは「90° で軸が入れ替わる」以外に説明が付かない。

修正は `trunk_ori_ref`: 誤差を回転ベクトル `e = log(R_des · Rᵀ)` で作る。
これは定義から世界系の量なので、どの方位でも正しい。
`kd` も `omega_world` に対してかかるので整合する。
回帰テストは `trunk_orientation_error_is_frame_correct_at_any_heading`
── 同じ機体ロールを 4 方位で与え、**大きさが一定で、載る世界軸だけが回る**
ことを見る。旧実装は yaw=90° で落ちる。

### 16.2 指標のほうのバグ 2 つ

修正しても 0.20 rad/s が **-69%** と出た。私の測定側である。

1. **ランプインを込みで平均していた。** 6 歩のランプで失うヨーは定常では
   取り返せないので、固定の不足として全ケースに乗る。前進が軒並み 91% だったのも
   これ(§15.3 で「ランプぶん」と推測は書いたが、直していなかった)。
   → 達成率はランプ終了時刻から測る。
2. **`euler_angles()` は ±π で折り返す。** 半回転を越えた瞬間、差分が符号ごと
   飛ぶ。0.20 rad/s が -69% と出たのは、**180° より多く回れるようになった**
   結果だった。
3. 加えて、旋回しながらの並進は**弦と弧が違う**。開始座標系での直線変位で
   測ると vx+wz 複合が 56% と出る(速度は正しいのに)。

→ 達成量は**機体座標系で毎 tick 積分**する。`travel[x, y, yaw]` を
最短角差分で累積し、継続時間で割る。転倒したケースは転倒直前の状態で
締める(転倒後の姿勢を、起きなかった継続時間で割っていた)。

これで vx+wz 複合が 56% → 98%/100% になった。**制御は最初から正しく、
測り方だけが間違っていた。**

### 16.3 「一歩で大きく旋回」は逆効果だった

ユーザ提案。歩周期を伸ばして一歩あたりの旋回量を稼ぐ。**測ったら悪化する。**

| t_step | wz | °/歩 | ankle_roll | |
|---|---|---|---|---|
| 0.55 | 0.6 | **18.9** | 59% | 生存 |
| 0.40 | 0.8 | **18.3** | 60% | 生存 |
| 0.40 | 1.0 | 22.9 | 141% | 転倒 |
| 0.55 | 0.8 | 25.2 | 201% | 転倒 |
| 0.80 | 0.6 | 27.5 | 139% | 転倒 |
| 1.10 | 0.8 | 50.4 | 135% | 転倒 |

**壁は「一歩あたり約 19°」で、旋回レートではない。** 20° を越えた所で
ankle_roll 使用率が 60% から 140%+ へ跳ぶ。したがって速く回りたければ
**歩調を上げる**のが正解で、一歩を大きくするのは逆。

ただし歩調にも下限がある: t_step=0.32 では 18.3°/歩(wz=1.0)でも落ちる。
遊脚 0.20 s で 20 mm を上げ切れない。**最速旋回は t_step=0.40 の 0.80 rad/s。**

先の `TURN_IN_DS`(単支持中は方位を保持し、二重支持で一気に回す)は
ほぼ中立だった(92→93 / 82→87 / 47→45 / 27→26%)。単支持ソールの
ねじり摩擦が効いているという仮説は支持されない。既定は維持、既定値は OFF でよい。

### 16.4 ankle_roll の飽和は原因ではなく結果

ROM を ±20° → ±40° に広げた変種で A/B。

| | wz=0.8 | wz=1.0 | wz=1.2 |
|---|---|---|---|
| stock | 102% 生存 (ankle 60%) | 94% 転倒 (141%) | 93% 転倒 (180%) |
| ±40° | 102% 生存 (**30%**) | 94% 転倒 (145%) | 91% 転倒 (139%) |

使用率が 60→30% に半減しているので ROM は確かに広がっている。**それでも
落ち方が 1 桁も変わらない。** ankle_roll の飽和は、倒れながら足裏が転がる
**結果**であって原因ではない。§4 の片足支持で同じ結論に達したのと同型で、
今後この数字を原因として読まないこと。

### 16.5 今の旋回性能

- 0.05 / 0.10 / 0.20 / 0.40 / 0.60 rad/s(t_step=0.55)── いずれも 100〜101%、生存
- 0.80 rad/s(t_step=0.40)── 102%、生存、tilt 0.005 rad、DCM 誤差 11.3 mm、
  自己干渉 0、open-loop 0、degraded 12

- 複合 vx=0.055 + wz=0.10 ── 98% / 100%

**前進の壁(0.109 OK / 0.145 転倒)はこの修正で動かない。** 座標系バグは

### 16.6 ベンチ再走(42 ケース)── 34/42 生存、生存した全件が追従も合格

| 群 | 通る範囲 | 落ちる所 |

## 17. kyo46rs2 に差し替えて一通り走らせた(2026-08-03)

### 17.1 2 モデルの差は 3 点だけ

同じ 16 関節・18 リンク・同じ名前。違うのは:

- **torso の質量 1.274 → 0.750 kg(−41%)。全体の質量差 6.630 → 6.106 kg はこれが全部。**
  ただし torso 重心は **49 mm 上がり**(z −20.9 → +28.3 mm)、
  **ixx +32%** / iyy +4% / **izz −13%**
- **hip_pitch のトルク上限 12 → 6 N·m**(knee は両モデルとも 12 のまま)

`KYO46RS2` プロファイルは `..KYO46RS` を継承するだけでよい(接地高さは
バーンイン後に実測するので寸法差は自動で吸収される)。

### 17.2 ベンチ 42 ケース: 30/42(v1 は 34/42)

**内側の性能は同一。** 前進 98%、後退 97%、横 90〜105%、旋回 ±0.40 まで
100〜101%、屈伸 10/20/40 mm、複合 vx+wz / vx+屈伸 ── すべて v1 と同じ数値。

### 17.3 hip_pitch のトルク半減は原因ではない(2×2 で分離)

hip_pitch の effort だけを入れ替えた URDF を作って 4 通り走らせた。

| ケース | rs hp=12 | **rs hp=6** | rs2 hp=6 | rs2 hp=12 |
|---|---|---|---|---|
| 後退 -0.109 | 97% 生存 | **97% 生存** | 転倒 | 転倒 |
| 旋回 0.60 | 101% 生存 | **101% 生存** | 転倒 | 101% 生存 |
| 旋回 0.80 高歩調 | 102% 生存 | **102% 生存** | 転倒 | 転倒 |
| 旋回 1.00 高歩調 | 転倒 | **100% 生存** | 100% 生存 | 転倒 |
| vx+vy | 99/93% 生存 | **99/93% 生存** | 転倒 | 転倒 |

**v1 の hip_pitch を 6 に落としても、5 件中 4 件で数値が完全一致する。**
残る 1 件(旋回 1.00)は下げたほうが生き残る ── 因果ではなく境界の感度。
逆に v2 の hip_pitch を 12 に戻しても回復するのは 5 件中 1 件だけ。

したがって v2 の後退は**質量分布**である。torso が 41% 軽いのに重心が 49 mm
上がり、ロール慣性が 32% 増えている ── 転ぶのが横方向系(横移動・複合 vx+vy・
旋回の横荷重)に集中しているのと整合する。

**この結論は「hip_pitch を 12 に戻せば直る」という自然な読みを否定する。**

なお、ここで書いた「上げるべきは torso 重心の高さ」という推奨は**§17.5 で
測って外れた**。相関を見て原因を名指ししただけで、実験していなかった。

### 17.4 v2 でも三重指令は通る

### 17.5 重心を下げても直らない ── 効いているのは torso の質量(2026-08-03)

§17.3 で「torso 重心が 49 mm 上がったのが原因だろう」と書いた。**測ったら違った。**

torso の慣性原点 z だけを動かした掃引(素の +28.3 mm から −80 mm まで):

| ケース | +28.3(素) | 0 | −20.9(v1 と同値) | −50 | −80 |
|---|---|---|---|---|---|
| 後退 -0.109 | 転倒 | 転倒 | 転倒 | 転倒 | 転倒 |
| 旋回 0.60 | 転倒 | 転倒 | 転倒 | **生存** | 転倒 |
| 旋回 0.80 高歩調 | 転倒 | **生存** | **生存** | 転倒 | 転倒 |
| vx+vy | 転倒 | 転倒 | 転倒 | 転倒 | 転倒 |

単調性が無く、一番下げた −80 mm がほぼ全滅。決定的なのは
**v1 と全く同じ重心位置(−20.9 mm)にしても後退と vx+vy が戻らない**こと ──
重心位置は原因ではない。

残る 3 つの差を 1 つずつ v1 の値に戻して切り分けた:

| ケース | v2 素 | v1 の torso 慣性ブロック丸ごと | **v1 の torso 質量のみ** | v1 の脚長 |
|---|---|---|---|---|
| 後退 -0.109 | 転倒 | 転倒 | 転倒 | 転倒 |
| 旋回 0.60 | 転倒 | 転倒 | **生存** | 転倒 |
| 旋回 0.80 高歩調 | 転倒 | 生存 | **生存** | 転倒 |
| vx+vy | 転倒 | 生存 | **生存** | 転倒 |

**torso 質量を 0.750 → 1.274 kg に戻すだけで 4 件中 3 件が回復する。**
重心と慣性テンソルまで一緒に戻すと旋回 0.60 を失う(重心を下げるのが
逆効果という上の結果と整合)。脚長 8 mm は 1 件も回復させない。

方向が直感と逆で、**torso は重いほうが安定**。torso は全体のわずか 12%
(v2)で、残り 5.36 kg は脚と腕にある。遊脚を振ったときの反作用を受け止める
のが torso なので、torso が軽いほど胴体が蹴られる。0.750 kg は 1.274 kg に
対してその比が 70% 悪い。

**後退 -0.109 はどの単独レバーでも戻らない。** torso でも脚長でもトルクでもない。

**したがってモデル側の改善余地は torso 質量であって重心高さではない。**
当面は v1(`ROBOT` 未指定が KYO46RS)で進める。

### 17.7 レンダラの穴 ── 円筒の底面が裏返っていた(2026-08-03)

ユーザ指摘:「後ろから見ると足首 Roll 軸の円柱(モータ)が透けている」。実際に
バグだった。円筒プリミティブは 12 角柱として組んでいるが、

```python
caps = [tuple(range(n)), tuple(range(n, 2 * n))]
```

**両方のリングが同じ向き(反時計回り)なので、キャップの法線がどちらも +z
になる。**上面はそれで正しいが、底面は内向きである。裏面カリングが
`n·(eye − centre) > 0` で判定するので、**底面は見えるべきときに消え、
隠れるべきときに描かれていた。**結果、円筒が三日月状の殻になって向こう側の
オレンジ(出力側)が透けて見える。底面のリングを反転して直した。

kyo46rs の URDF は visual が**すべてプリミティブ**(円筒 32・箱 17・球 1、
メッシュ 0)なので、このバグが全身の全モータに乗っていた。

STL メッシュ側(`emit_mesh`)にも同型の問題がある。裏面カリングは
**閉じていて巻き方向の揃ったメッシュでしか正しくない**が、STL はどちらも
保証しない。カリングをやめ、法線を視点側へ反転して両面描画にした
(painter's が遠→近で塗るので、閉じた形状は手前が奥を上書きして正しく出る)。
G1 で A/B すると胴と骨盤の点状の穴が消え、コストは +18%(19.3 → 22.8 s)。
旧挙動は `CULL=1` で再現できる。

**この 2 つは制御には一切影響しない。** ただし動画は結果の判定に使っており、
「モデルが痩せて見える」を実機形状の問題と読み違える余地があった。

### 17.8 kyo46rs の胴体形状を kyo46rs2 のものに差し替えた(2026-08-03)

torso は 0.14 × 0.10 × 0.22 の箱で、形のある手足の横で寸胴のスラブに見えていた
(実構造より前後に 40 mm 厚く、くびれが無い)。kyo46rs2 は形のある殻を持って
いて、**2 機は torso フレームを共有する** ── torso にぶら下がる関節
(hip_yaw / shoulder_pitch / head)の原点がすべて一致するので、
合わせ込みのオフセット無しでそのまま載る。

**visual のみ意図的に差し替えた。**衝突形状は同じ箱のまま(kyo46rs2 も同じ箱を
使っているので 2 機の衝突は依然として同一)、慣性は kyo46rs 自身のもの
(1.274 kg)を維持 ── §17.5 で「v2 の軽い torso が後退と横移動の余裕を
奪っている」と測ったので、そこは持ち込まない。

「visual は衝突にならない」も仮定ではなく確認した: articara のローダは
`link.collisions` からのみメッシュを落とし、visual には触らない。差し替え後に
0.80 rad/s 旋回を再実行して**数値が完全に一致**する(102%、DCM 11.3 mm、
ankle_roll 60%、degraded 12、自己干渉 0)。

このリポジトリ初のメッシュ。同じクリップの描画が 47 s → 99 s になる。

## 18. 外乱ベンチ ── 束縛条件を測りに行って、4 つの仮説を潰した(2026-08-05〜06)

「一通り歩けるようになったので外乱耐性を付けたい」から始めた。**制御を足す前に
測る道具を作る**ことにして、結果として制御は一行も足していない。得られたのは
**この機体の転倒は着地後の接触喪失で決まる**という束縛条件と、それを測る量。

### 18.1 ベンチの作り

`examples/kyo46rs_walk.rs` に 1 発のパルス外乱、`scripts/kyo46rs_bench.py --push`
に掃引を足した。設計上の判断が 3 つある。

**① 力ではなく力積 [N·s] で刻む。** 足首戦略で吸える量が `m·ω·d_cop` で書ける
から。この機体では前後 1.81、横 **0.70** N·s(6.63 kg × 5.585 rad/s × 0.049 /
0.019 m)。力で刻むと duration が隠れて 2 つの run が比較できない。

**② 位相を固定する。** 両足支持と単脚支持で吸える量が違い、単脚支持では立脚が
左右どちらかでも違う。`PUSH_STEP` / `PUSH_AT` / `PUSH_SUPPORT` で指定し、
立脚を入れ替えたミラーセルを常に併走させる。

**③ パルスが位相をまたいだら警告する。** `PUSH_DT=0.10` に対し `t_ds=0.20` なので
`PUSH_AT=0.5` だとパルス終端が離地に重なる。これで DS の限界が SS より低く出て
いた(0.349 対 0.607)。DS セルは `PUSH_AT=0.25` に固定した。

方向の CoP 余裕は「優勢な軸の半幅」ではなく**箱からの射出距離**
`min(half/|成分|)`。45° は 1.81 でも 0.70 でもなく 1.00 N·s。最初は度を
`cos()` にラジアンとして渡していて、`back` と `right` が逆の値を拾っていた。

再現(トレース CSV は大きいので版管理していない。この 1 行で作れる):

```
T_SS=0.35 T_DS=0.20 STRIDE_RAMP=6 ARM_PITCH=0 LIFT_H=0.02 PHASE_BY_CONTACT=0 \
N_STEPS=20 T=15.0 VX=0.055 ADAPT_STEP=0 K_DCM=2.0 FIRST_SWING=0 \
PUSH_DEG=90 PUSH_STEP=6 PUSH_AT=0.5 PUSH_SUPPORT=ss PUSH_IMPULSE=0.20 \
TRAJ_CSV=csv/push_0.20.csv ./target/release/examples/kyo46rs_walk

# 掃引(結果は csv/push_criteria.csv、csv/push_sweep_b_lateral.csv に版管理)
python3 scripts/kyo46rs_bench.py --push-sweep --push-conditions "adapt0 k2.0" \
  --grid-step 0.05 --grid-max 2.00
```

`PUSH_DEG=0` が前方向、`PUSH_STEP=7` が立脚を入れ替えたミラー。動画は
`TAU_JOINTS` で下段の帯を前額面(`*_hip_roll_joint` / `*_ankle_roll_joint`)に
切り替えてから `examples/render_com_squat_video.py <traj.csv> <out.mp4>`。

### 18.2 生存は力積に対して単調でない ── 二分探索は使えない

`left ss (mirror)` を 0.05 刻みで回すと:

```
0.30〜0.45 生存 / 0.50 転倒 / 0.55, 0.60 生存 / 0.65〜1.00 転倒
```

さらに二分探索の途中で **0.550 生存 / 0.551 転倒**。境界は閾値ではなく斑。
§17.2 の「旋回 0.80 は落ちるが 1.00 は通る」と同じ現象が外乱軸にも出る。

**最初に作った二分探索版のベンチは条件比較に使えない。** 返す値は斑の中の任意の
1 点で、`ADAPT_STEP` を変えて 0.607 → 0.540 になってもそれは効果ではない。

推定量を**固定格子ラダー**に置き換えた。`safe` = それ以下の全点が生存した最大値、
`fail` = それ以上の全点が転倒した最小値、`fail/safe` が斑の幅。**格子刻みが
そのまま誤差棒**なので、格子は全セル・全条件で同一でなければならない ── 途中で
作った適応ラダー(幾何ブラケット + 細分)は、セルごとに probe 点が変わるので
比較にならず、`left ss (mirror)` で `safe=0.516` と報告した(0.50 が格子に
無かっただけで、実際には 0.50 で転ぶ)。

### 18.3 (b) 着地点補正と CoP ループ ── 効かない、下げるのは有害

横方向 6 セル × {ADAPT_STEP 0/1} × {K_DCM 2.0/1.0/0.5}、864 run。

| 条件 | 最弱セル | 中央値 | 合計 |
|---|---|---|---|
| adapt0 k2.0(既定) | 0.450 | 0.600 | 3.80 |
| adapt0 k1.0 | 0.300 | 0.650 | 3.75 |
| adapt0 k0.5 | 0.200 | 0.450 | **2.40** |
| adapt1 k2.0 | 0.500 | 0.600 | 3.75 |
| adapt1 k1.0 | 0.350 | 0.600 | 3.75 |
| adapt1 k0.5 | 0.200 | 0.500 | **2.45** |

**着地点補正は耐外乱を上げない。** adapt1 の 3 列は adapt0 と区別できない。
§14.3 が「着地点補正は CoP ループを降格して初めて効く(stride 0.06 で 26 → 92
歩)」と測ったのは**歩数**であって、耐外乱では同じことが起きない。

**`k_dcm` を下げるのは耐外乱では明確に有害**(合計 −35%、6 セル中 5 セルで一貫)。
斑も広がる(`fail/safe` が 3.25〜3.50 倍)。運転点の追従(5.7 対 17.1 mm)でも
k2.0 が勝つので、既定 k_dcm=2.0 はこの軸でも支持された。

最良条件は 6 セルで 5 通りに分かれる。**ここにチューニングで取れる余地は無い。**

### 18.4 両足支持の左右差 1.5 倍は「足の役割」── 対処不要

DS で left 0.65 / right 0.95 が全 6 条件で一貫していた。`PUSH_STEP` を 1 つ
ずらすと入れ替わり、`FIRST_SWING` を反転させても入れ替わる。値は 2 水準しか
取らない(0.60〜0.65 と 0.95〜1.00)。

**機体の左右ではなく、その両足支持で「これから荷重が乗る足」がどちらかで決まる。**
`t_ds` の間に CoP が離脱足から着地足へ移動しているので、着地足側には広がる支持
多角形が待っており、離脱足側には計画上もう戻れない。LIPM 計画の当然の帰結で、
直すものは無い。「左側だけ余力を使えていない、伸びしろ 0.65→0.95」と一度書いたが
**誤り**。

### 18.5 潰れた仮説 4 つ

| 仮説 | 反証 |
|---|---|
| CoP 箱の飽和が律速 | 全セル・全点で 1.00。**0.15 N·s で無傷に生き残る run も 1.00**。平常時から飽和していて識別力が無い |
| 自己干渉が離散スイッチ | 転倒 6 点のうち 3 点が `selfcol=0`。倒れる途中で腕が股関節に当たる**結果** |
| ankle_roll 可動域が壁 | ±25/30/40° の URDF 変種で測定。生存数は 8→11/14 に増えるが **`safe`(0.15)も天井(≥1.20 で全転倒)も動かない** |
| 摩擦錐(滑り) | 転倒側の方が**滑っていない**(40 ms 対 生存 135〜150 ms)。地面側の摩擦利用率は MuJoCo が錐を守るので全 run 1.00 に飽和 |

ankle_roll について: 生存は全て ≤137%、転倒は全て ≥148% と**14 点で完全に
分離する**。ここから「飽和が原因」と一度結論したが、±40° にしても転倒時は同じ
「限界の 1.5 倍」(50〜60°)に到達する。**関節限界が変位を止めていたのではなく、
倒れる過程で足裏が転がっているだけ。** 相関は完璧でも因果ではない。

摩擦について: `slip` は `friction_mu`(WBC の想定 0.6)が分母。地面は 0.7 なので
`slip=1.167` は「地面側の錐に張り付いている」を意味する。**`friction_mu` を掃引
すると分母が動くので、それで滑りを判定してはいけない。** 分母 2 系統で出すように
した。

### 18.6 束縛条件 ── 着地後の接触喪失

0.20(転倒)と 0.15 / 0.30(生存)のトレースを重ねると、分岐は着地の直後。

| | 総鉛直力 最小 | ピーク | 体重の 0.5 倍未満の時間 |
|---|---|---|---|
| 0.15 生存 | 56.4 N | 1.22× | **0 ms** |
| **0.20 転倒** | **0.0 N** | **2.77×** | **100 ms** |
| 0.30 生存 | 41.0 N | 1.41× | **0 ms** |

```
横外乱 → 遊脚が計画外の水平速度を持って着地
      → 着地衝撃が体重の 2 倍超
      → 機体が跳ね、両足の合計荷重が体重の半分未満に 65〜250 ms 落ちる
      → その間 QP は接地を仮定して解き続ける(degraded は出ない)
      → 弾道飛行中に姿勢が発散
```

**押された量が支配変数ではない。** 着地の瞬間に脚がどの位相にいるかで決まる。
0.20 は「掴めないが離れもしない」最悪の位相関係に入る。これが斑の正体。

### 18.7 判定量は浮上時間 ── 衝撃ではない

全 14 セル × 格子 0.05〜2.00(560 run)で 2 候補を比較した。

| | セル内順序が成立 | 生存側の範囲 | 転倒側の範囲 |
|---|---|---|---|
| 着地衝撃(ピーク) | **11/14** | 1.63〜2.22× | 1.74〜2.51× |
| **浮上時間(積分)** | **14/14** | **0〜30 ms** | **20〜95 ms** |

衝撃は `fwd ds` で **生存 2.22× / 転倒 1.79×** と逆転する。ピークは 1 tick の
外れ値に振られるが、浮上時間は**接触を失っていた総時間** ── QP が持っていない
状態に機体が置かれた時間そのもの ── なので機構との対応も直接的。

**基準: 押された後、両足の合計鉛直力が体重の半分を下回る時間を 50 ms 未満に
保つこと。** `safe` は斑で 0.05 N·s 刻みしか動かないので変更の評価に使えないが、
浮上時間は連続量なので同一セル・同一力積のペア比較ができる。

## 19. 束縛条件の追跡 ── 6 つ潰し、判定量を作り直し、着地点補正を棄却した(2026-08-06〜07)

§18 は「転倒は着地後の接触喪失で決まる」で終わっていた。そこから先を詰めたら
**その因果が逆だった**ことが分かり、判定量を 3 回作り直すことになった。

### 19.1 §18 の機構は因果が逆だった

§18.6 の「着地衝撃 2.8x → 跳ねる → 浮上 → 転倒」は、衝撃が**いつ**出るかを
見ていなかった。

| | ピーク時刻 | 着地からの経過 | そのときの傾き |
|---|---|---|---|
| 0.15 生存 | 5.060 | +0.015 s | 0.001 rad |
| **0.20 転倒** | **5.735** | **+0.690 s** | **0.494 rad (28 deg)** |
| 0.30 生存 | 5.205 | +0.160 s | 0.044 rad |

**転倒 run の 184.8 N は、28 度傾いた機体が床に叩きつけられた音。** 浮上時間も
同じで、総荷重が体重の半分を割るのは t=5.40、そのとき傾きは既に 0.122 rad。
**傾きの発散が先、浮上が後。**

遊脚の着地時の垂直速度も測った ── 3 本とも **-0.198 / -0.202 / -0.184 m/s** で
同一。`swing_touchdown_vz`(§18.9 で次手と書いたもの)はまさにこの量を整形する
ノブなので、**移植しても分かれ目に触れない。取り下げ。**

### 19.2 早期窓 ── 転倒は押した瞬間には決まっていない

指標を `[t_push, t_push + W]` に閉じ込め、W を広げながらどこで分離が現れるかを
見た(既存トレースからのオフライン計算)。

| W [s] | 分離する量 |
|---|---|
| 0.10 | **なし** |
| 0.20 | DCM 誤差のみ(14.3 対 10.2 / 3.1 mm、マージン薄い) |
| 0.30 | + ピーク荷重 |
| 0.40 | + 最小荷重 |
| **0.50** | **+ 傾き、浮上時間** |

押し後 100 ms では転倒する run が**どの指標でも最悪でない**。むしろ生存した
0.30 のほうが傾き 0.020 対 0.010、最小荷重 0.63 対 0.90 と悪い。

そして 0.5 s 後に何があるかというと、**次の歩の荷重移行**。

```
t=5.35   0.30 生存: fzL  0.0 / fzR 64.1   <- 右足に完全移行
         0.20 転倒: fzL 41.7 / fzR 45.0   <- 両足に半々のまま
t=5.40   0.30 生存: fzL  0.0 / fzR 65.2   <- 定常
         0.20 転倒: fzL  0.0 / fzR 12.3   <- 両方失う
```

**外乱そのものは生き延びていて、その後の 1 歩で落ちている。**
ドライバは `PUSH_WINDOW_S`(既定 0.20)で早期窓の指標を全部二重に出すようにした。

### 19.3 原理確認 ── トルク 3 倍は「悪化」する(**§20 で取り下げ**)

> **この節の結論は誤り。** 24 点格子の生存数は、物理的に無意味な摂動だけで
> ±2 振れる(§20)。10→7 も 10→12 も誤差の中で、悪化も改善も測れていない。
> 以下は測定手順の記録としてのみ残す。飽和しているのが脚ではなく腕という
> 観測(トルクの実測値)と、`TORQUE_SCALE` が QP の箱しか動かさないという
> 事実は有効。

トルクは QP の箱(`rig.torque_max`)と MuJoCo の `forcerange` の 2 箇所にあり、
`TORQUE_SCALE` は**前者しか動かさない**(出せない指令を計画する実験になる)。
両方を上げるには URDF の effort を変える。脚/腕/両方の 3 変種を作った。

まず飽和しているかを確認したら、**飽和しているのは脚ではなく腕**だった:

| 窓 | 飽和 |
|---|---|
| 押す前 | なし(最大 hip_roll 54%) |
| 押し +0.20 s | `right_shoulder_pitch` 1 tick。脚は最大 60% |
| +0.40〜0.60(発散) | `right_shoulder_pitch` **19/40 tick**、脚は 2 tick |

24 点格子(左 ss、0.05〜1.20)の結果:

| 条件 | 生存パターン | 生存 |
|---|---|---|
| ベースライン | `...XX......XX.XXXXXXXXXX` | **10/24** |
| 脚のみ 3 倍 | `.....XX..XXXXXXXXXXXXXXX` | **7/24** |
| 腕のみ 3 倍 | `...X....X.X....XXXXXXXXX` | 12/24 |
| 全部 3 倍 | `....X.XXXXXXXXXXXXXXXXXX` | **5/24** |

**脚を強くすると悪化する。** 同じ 0.30 N·s(ベースライン生存 / 脚 3 倍 転倒)を
早期窓で比べると、傾き 0.016 → 0.057、摩擦利用率 0.84 → 1.00(滑走 10 ms)、
総荷重 最小 0.63x → 0.15x、ピーク 1.37x → 3.00x、degraded 4 → 17。

理由: **トルクを増やしても地面が返せる力は増えない。** 水平力は摩擦錐、圧力中心

支えられない」解が実行可能領域に入り、ソルバはそれを選べてしまう。degraded が

**接線力の不足ではない。**

### 19.5 判定量 ── CoP が足裏の縁から離れられるか

荷重移行を tick 単位で並べたら、判別しているのは足裏内の CoP 位置だった
(`copRy`、半幅 19 mm):

```
             0.20 転倒    0.30 生存
5.31 移行 →   -17.9        -18.9
5.32          -18.0         -6.0   <- 縁から離れる
5.38          -18.1         -2.2
5.55          -19.0         -3.5
```

生存 run は移行の 10 ms 後に CoP が中央(-2〜-4 mm)に落ち着き、総荷重が 1.00x に
固定される。転倒 run は最後まで縁に張り付き、荷重が 0.00〜1.97x で振動する。
**縁にいる足は自分の圧力を調整できない = 重心を制御する権限がゼロ。**

指標: **単脚支持への突入を起点に、その後 100 ms のうち立脚 CoP が縁
(半幅の 90% 以上)にいた割合。** 起点は「両足 → 単脚」であること ── 逆の遷移
(単脚 → 両足)では 3 本とも 100% になり判別できない(両足支持では各足の CoP が
内側の縁に乗るのが正常)。

| 力積 | 縁滞在 | 離脱まで | 結果 |
|---|---|---|---|
| 0.15 | 0/20 (0%) | 0 ms | 生存 |
| **0.20** | **20/20 (100%)** | **離れない** | **転倒** |
| 0.30 | 2/20 (10%) | 10 ms | 生存 |

**同じ CoP という量でも、最大値ではなく「縁から離れられるか」を見ると識別力が
出る。** §18.5 で「CoP 箱の飽和は無害な run でも 1.00 で識別力なし」と書いたのは
最大値の話で、そこは正しい。

### 19.6 着地点補正の再評価 ── 棄却(私の過度な一般化つき)

## 20. ベンチ自身のノイズを測ったら、いくつかの結論が消えた(2026-08-07)

「トルクを 3 倍にして悪化するのは、制御が正しければ起きないはずでは」という
指摘から始まった。**正しい指摘で、実際には悪化を測れていなかった。**

### 20.1 まず実験の作りを疑った ── そこは問題なかった

URDF の `effort` を変えると何が変わるかを確認した。MJCF の `<motor>` は
`gear="1"` 固定で、`effort` から作られるのは `forcerange`(クランプ)だけ。
**同じ `data.ctrl` に対するプラントの応答は変わらない。** `rig.torque_max`
(QP の箱)と `forcerange` の両方が同じ値で動くので、実験の作りは正しい。

`box_bound` も確認した ── `Task::in_range`、つまりハード不等式であって
コスト項ではない。緩めれば実行可能集合が広がるだけで、目的関数は変わらない。

### 20.2 次に「解が非一意なのでは」と考えた ── これも違った

非活性な制約(9% しか使っていない脚のトルク箱)を緩めて解が変わるなら、解が
一意に決まっていないのでは、と考えた。**指摘のとおりこれは筋が悪い** ──
冗長な機体で解が一意でないのは正常で、問題があるとすれば「解集合に不適な解が
入っている = 制約か目的関数が区別すべきものを区別していない」ほう。

そして測ったら、非一意ですらなかった。トルク上限を 6.0 → **6.0001** N·m
(0.0017%)にして t=0 を比べると:

| 量 | 差 |
|---|---|
| 接触力 6 成分(左右) | **完全一致** |
| QP の計画 CoP(左右 x/y) | **完全一致** |
| 合力 3 成分 | **完全一致** |
| 関節トルク | `left_ankle_pitch` のみ **1.0e-05 N·m** |

内点法が返す中心パス上の点が、制約の摂動に比例してわずかに動いただけ。
**QP は正しく、ほぼ一意に解いている。**

### 20.3 「歩容がカオス的」も誤りだった

1e-05 rad の初期差が t=5.25 で 10 rad まで育っていたので、指数発散だと判断し、
0.5〜4.0 s で回帰して「成長率 +1.32 /s、倍加時間 0.53 s」と報告した。**誤り。**

`|Δq|` の時系列は 1.6e-4 → 5.2e-1 → 3.4e-2 → 2.7e-2 と**振動**していた。これは
指数成長ではなく、**わずかな時間ずれが遊脚の速い区間でスパイクしている**だけ。
振動するデータに直線を当てはめて成長率を出していた。

決定的な反証: 運転点 `VX=0.055`、外乱なし、40 歩・26 秒を `MU_GROUND` の
1e-7 相対摂動 10 通りで走らせると、**10 本すべて DCM 誤差 5.2 mm で同一、
全部生存**。カオスなら 26 秒で別物になっているはず。

`VX=0.091`(前進の壁の近く)では同じ摂動で DCM 誤差が 5.2〜10.1 mm にばらける。
**鋭敏なのは性能の境界付近だけ** ── 吸引域の境界であって、カオスではない。

### 20.4 本当の答え ── ベンチのノイズ

同じ 24 点格子(左 ss、押しあり)を、`MU_GROUND` の 1e-7 相対摂動 5 通りで:

```
mu=0.700000000  ...XX......XX.XXXXXXXXXX  10/24
mu=0.700000100  ............XXXXXXXXXXXX  12/24
mu=0.700000200  ..............XXXXXXXXXX  14/24
mu=0.700000300  ............XXXXXXXXXXXX  12/24
mu=0.700000400  ...XX.......X.XXXXXXXXXX  11/24
```

**摩擦係数の 1000 万分の 1 の変化で、生存数が 10〜14/24 に振れる。** 個々の
格子点(0.20、0.25 など)が転倒したりしなかったりする。

**これが 1 セル比較の誤差棒。** `--repeat N` で測れるようにした。

## 21. ステップタイミング適応と、実装せずに済ませた 2 件(2026-08-07〜08)

§20 で「制御側で唯一まだ触っていないのはステップのタイミング」と書いた続き。
実装して測り、外部レビューを 4 系統かけ、その指摘を検証した。**結果として 1 件が
効き、2 件を実装前に落とし、1 件は実装したが効かなかった。**

### 21.1 ステップタイミング適応 ── 効く

`dcm::step_timing`。単脚支持中の DCM 閉形式を残り時間について反転するだけ:

```text
xi_eos = p + (xi_meas - p) exp(omega tau)
tau    = ln((xi_eos - p) / (xi_meas - p)) / omega
```

**除算と対数 1 回。QP も MPC も要らない。** 目標は計画自身の `xi_eos`、`p` は
立脚の ZMP。2 軸に対して未知数 1 つの過決定なので `ADAPT_TIME_AXIS` で軸を選ぶ
(既定 1 = 横、この機体が倒れる軸)。単体テスト 3 件。

**最初の実装は既定歩容を壊した。** 外乱ゼロでも 54〜60 tick・約 500 ms 再計時
する ── 目標と実測は定常でも一致しないので、ソルバが毎 tick「あと数 ms」と
言い続ける。42 ケースの指令ベンチが **34/42 → 26/42**。DCM 誤差が閾値を超えた
ときだけ発動する `ADAPT_TIME_TRIG`(15 mm)を足して **34/42 に復帰、42 ケース
すべてがケース単位で一致**した。

効果(14 セル × 24 点 = 336):

| | 生存 | CoP 縁滞在 |
|---|---|---|
| `timing off` | 232/336 | ─ |
| **`timing on`** | **259/336** | 改善 36 / 悪化 29 |

**+27 / -1、14 セル中 13 で改善または同等**、5 セルで `safe` 上昇。14 セル合計の
誤差 ±7 に対し 3.6σ。着地点補正(改善 26 / 悪化 83)と同じ土俵で、今週初めて
効いた制御側の変更。

### 21.2 レビューの指摘 ── タイミング適応は倒れるケースでは無言

4 系統(制御理論 / 機体設計 / 測定手法 / コードベース調査)に同じ実測値を渡して
検討させた。**価値があったのは 1 つの反証可能な主張**:

> `step_timing` は DCM が ZMP の反対側にあると解を返さない。それはまさに横に
> 押されて倒れるケースではないか。だとすれば +27 は「遅れた歩を直した」効果で
> あって、倒れる歩には一度も介入していない。

計測器を足して測った:

| 力積 | 解けた | 棄却 | 結果 |
|---|---|---|---|
| **0.20** | 8 | **75** | **転倒** |
| 0.30 | 0 | 0 | 生存 |
| 0.65 | 1 | 0 | 生存 |
| 0.90 | 1 | 0 | 生存 |

**裏付けられた。転倒する run では 90% の tick で棄却されている。**

そこで戻り値を `Option<f64>` から列挙型にした。`Unreachable` は「答えが無い」
ではなく **「待つのをやめろ」という答え**なので、`None` に潰してはいけない:

```rust
pub enum StepTiming { Time(f64), Unreachable, Degenerate }
```

### 21.3 角運動量タスク ── 4 run で実装せずに済んだ

§18.9 で本命と書き、§19 で保留にしていた件。**実装前に反証する**方針で、単脚
支持突入時のロール軸重心角運動量 `h_x = (A_G v)[0]` を測った:

| 力積 | 突入時 `h_x` | 1 秒間のピーク | 結果 |
|---|---|---|---|
| 0.15 | +0.066 | 0.120 | 生存 |
| **0.20** | **+0.178** | **1.100** | **転倒** |
| 0.30 | +0.087 | 0.139 | 生存 |
| 0.65 | +0.049 | 0.122 | 生存 |

突入時の差は 2〜3.6 倍だが、ピークは **9 倍**。つまり `h_x` は転倒とともに育つ量
で、原因か結果かはこの 4 点では決まらない。**決め手は育つ先の大きさ**:
1.10 kg·m²/s。腕は片側 0.62 kg・肩から手先 0.25 m なので両腕を 1 m/s で振っても
0.3 kg·m²/s 程度、しかも **肩・肘とも矢状面軸なのでロール成分は原理的にゼロ**。

**実装しない。** 1 日分の実装を 4 run で回避した。§18.9 の理由づけ(接触喪失)は
§19.1 で取り下げているので、そこには印を付けた。

### 21.4 判定量は 1 歩では足りない

CoP 縁滞在は「単脚支持突入後 100 ms」で測っていた。タイミング適応は**その突入
時刻そのものを動かす**ので、指標が介入を過小評価する(+27/-1 に対し 36:29)。
2 歩目でも測ると:

| 力積 | 1 歩目 | 2 歩目 |
|---|---|---|
| 0.15 | 0% | 0% |
| 0.30 | 10% | **0%** |
| 0.65 | 35% | **0%** |
| 0.20(転倒) | 100% | 到達せず |

**生存 run は 2 歩目で全て 0% に戻る。** 1 歩目の 10〜35% は回復途中の一過性で、
指標はそれを減点していた。以後は 2 窓で見る。

### 21.5 reduced-step 反射 ── 実装したが効かない

§21.2 の `Unreachable` を「歩を最短で打ち切る」に落とす(`ADAPT_TIME_CUT`、
既定 OFF)。文献の reduced step 反射で、縁に張り付いた足に乗り続けるより両足
支持の広い多角形に渡すほうが良い、という理屈。

測定設計も §20 の教訓を入れ替えた:

- 格子を**各セルの境界 ±4 点(9 点)**に絞る。境界から遠い点は何も動かない
- **条件間では同一格子**(セル間だけ中心が違う)。適応ラダーが壊した性質(§18.2)
- **反復 3** を本測定に組み込み、効果とノイズ床を同じ実行から出す

結果(14 セル × 9 点 × 2 条件 × 3 反復 = 756 run):

| | 生存 | CoP 縁滞在 |
|---|---|---|
| `timing on` | 103/126 | ─ |
| `timing cut` | 102/126 | 改善 3 / 悪化 2 |

**14 セル中 11 で反復ごとの値まで完全一致。効果なし。**

理由は `ADAPT_TIME_TRIG=15 mm` のゲートが先に効いていること ── `Unreachable`
が 75 tick 出るのはゲート通過後の話で、境界近傍の 9 点の多くではゲートが開かない。
加えて反射が発火しても `t_ss × 0.6` までしか短縮できない(`ADAPT_TIME_MIN`)。

切り分けは 1 パラメータ(`ADAPT_TIME_TRIG` を 5 mm、`ADAPT_TIME_MIN` を 0.3)
だが、前者は既定歩容を壊す側なので **42 ケースの対照が必須**。

### 21.6 格子を絞ったらノイズ床も下がった

| | 格子 | ノイズ床(1 セル) |
|---|---|---|
| §20 | 全域 24 点 | **±2** |
| §21.5 | 境界 ±4 点の 9 点 | **0〜3、大半は 0〜1** |

境界から遠い点を捨てたので、振れる点の割合が減った。情報量あたり約 3 倍効率が
上がっている。そして今回は **「効果なし」を、ノイズ床を同時に測った上で
言えている** ── §20 で 4 件を取り下げた原因が手順から消えた。

## 22. 可変両足支持 ── 制御量は動かせる、結果は変わらない(2026-08-08)

§21.7 の残り 6 件から「可変両足支持」を選んで実装した。**結論は reduced-step
反射と同じ ── 狙った量は完全に制御できるのに、生死は変わらない。** そして
そこから、今日繰り返している探索方法そのものへの疑いが出た。

### 22.1 事前確認 ── 8 点で完全に分離した

`t_ds = 0.20` は定数(`gait.rs:111` でスライスを作る時点)。つまり**片足への
コミット時刻が押される前に決まっている**。そして §19.2 で分岐はそのコミットの
瞬間だと分かっている。

コミット(DS→SS)の瞬間の、DCM の「次の立脚足からの横オフセット」(内側が正):

| 力積 | 結果 | off_y |
|---|---|---|
| 0.10 / 0.15 | 生存 | **+7.7 / +7.8 mm** |
| 0.30 / 0.45 | 生存 | **+3.3 / +8.9** |
| **0.20 / 0.25** | **転倒** | **-4.3 / -11.9** |
| **0.65 / 0.90** | **転倒** | **+23.2 / +23.9** |

公称値 `b_y = l_p / (1 + exp(omega t_ss))` = 99.4/8.06 = **12.3 mm**。

**生存は +3〜+9 mm の帯に全部入り、転倒は両側に外れる。** 両足支持中に DCM は
前の立脚足から次へ向かうので、`+23` は「まだ寄ってきていないのにコミットが
早すぎる」、`-4〜-12` は「既に通り越しているのにコミットが遅すぎる」。
**固定 `t_ds` が両方向に外している。**

### 22.2 実装(`ADAPT_DS`、既定 OFF)

DCM が公称オフセットに到達したら DS を切る。到達していなければ上限まで開く。
`ADAPT_DS_TRIG`(15 mm)でゲート ── §21.1 と同じ規律で、外乱なしでは 1 tick も
再計時せず既定歩容は完全一致。

**実装で 2 回外した:**

- **片側しか書いていなかった。** 最初は「到達したら切る」だけで、`+23 mm`
  側(延長が要る)には一度も発動しなかった。事前確認で両側に外れると分かって
  いたのに。
- **延長の off-by-one。** `retime(i, t + dt)` は境界を次の tick 丁度に置くので、
  `index_at` が次のスライスを返し、分岐が二度と走らない ── 1 run あたり
  ちょうど 1 回の再計時で、オフセットが動かなかった。**上限まで開いておいて
  到着で閉じる**方式に変えて解決。

### 22.5 探索方法そのものへの疑い

今日、生存と転倒を**分離する量**を 6 つ見つけた。**動かせた 3 つはいずれも結果を
変えなかった。**

| 分離した量 | 分離の質 | 動かした結果 |
|---|---|---|
| CoP 箱の飽和 | ─ | 平常時も 1.00、識別力なし |
| ankle_roll 使用率 | **14 点で完全** | ±40° にしても限界も天井も不変 |
| 摩擦利用率 | ─ | 錐を 3.75 倍にしても不変 |
| 着地衝撃 / 浮上時間 | 11/14、14/14 | 転倒の結果だった(§19.1) |
| **コミット時の横オフセット** | **8 点で完全** | **揃えても 4 点とも転倒** |
| コミット時の前後オフセット | 8 点中 7 点 | 未検証 |

**「分離する量を見つけて動かす」ループを 5 周して 5 回とも外した。**

分離する量が次々見つかるのは当然で、転倒に向かう軌道はあらゆる量で正常軌道から
離れていく。**問題は、そのどれが操作可能な原因かを、分離の観察からは区別
できない**こと。相関を見つけて動かす、を繰り返す限り当たるかどうかは運になる。

6 周目(前後オフセット)に入る前に方法を変える。候補:

- **後ろ向きに解く。** 転倒 run のコミット時点の状態を、生存 run の状態で
  置き換えたら助かるか(状態注入)。助かるなら原因はコミット時点の状態の中に
  あり、助からないならそれ以降にある。**分離量を 1 つずつ試すより、原因の
  所在を先に二分できる。**
- **効いた唯一の手を理解する。** タイミング適応の +27 が具体的にどの run を
  どう救ったのかを追う。効く介入の共通性が見えれば、次の候補を分離量からでは
  なく機構から選べる。

## 23. 介入実験 ── 原因の所在を消去法で決め、壁が数値になった(2026-08-08)

§22.5 で「分離量を見つけて動かす」探索を打ち切ると決めた。代わりに**介入**した
── コミットの瞬間に矯正力積を加え、状態のどの部分を動かせば助かるかを掃く。
相関の観察ではなく因果の検定なので、**外した分離量を 1 つずつ試すより先に
原因の所在を二分できる。**

機構は既存の `apply_external_force` の使い回しで足りた(`FIX_DV` / `FIX_TAU` /
`FIX_AT_S`)。

### 23.1 コミット時点では手遅れ

転倒する 4 点(0.20 / 0.25 / 0.65 / 0.90 N·s、横方向・単脚支持)に対し、
コミット(DS→SS)の瞬間に:

| 介入 | 掃引幅 | 救えた |
|---|---|---|
| 重心速度 | **±0.15 m/s**(元の外乱の 5 倍) | **1/4** |
| 角運動量 | **±1.5 N·m·s**(自身のピーク 1.42 を超える) | **1/4** |

浮遊基底の 6 自由度すべてに、外乱よりはるかに大きい介入をしても 3/4 は救えない。
**コミット時点の基底の状態は、原因が住んでいる場所ではない。**

これで §22.4 の 6 個目(前後オフセット)を試す必要も消えた ── 前後・横どちらの
オフセットも重心速度の関数なので、**動かしても救えないことが試す前に分かる。**
分離量を 1 つずつ潰していたら 6 個目・7 個目と続いたところを、72 run で切った。

### 23.2 では、いつなら間に合うのか

同じ矯正を押しからの経過時刻で掃く(横方向 dv、`{±0.05, ±0.10}` の best):

```
  +s:    0.05  0.10  0.15  0.20  0.25  0.30  0.35  0.40
imp=0.20       .     .     .     .     .     .     X     X
imp=0.25       .     .     .     .     .     .     .     .
imp=0.65       .     X     .     X     X     X     X     X
imp=0.90       .     X     X     X     X     X     X     X
```

(押しは t=4.930、コミットは +0.38 s。`.` = 救えた)

**大きい外乱ほど窓が短い。** 0.90 N·s は押した **50 ms 後**までしか救えない。
0.20 N·s には 300 ms の猶予がある。**外乱の大きさと許容遅れが強く逆相関する。**

§19.2 の「押し後 100 ms では転倒 run が判別できない」と矛盾しない ── 判別
できないのは**観測**の話で、介入の可否は別。0.90 N·s は 50 ms の時点で既に運命が
決まりつつあるが、そのことは観測量に出ていない。

### 23.3 壁が数値になった

最悪ケース(0.90 N·s)を救う条件:

```
50 ms 以内に、重心速度を 0.10 m/s 動かす
 -> 力積 0.10 * 6.63 = 0.66 N*s を 50 ms で -> 水平力 13 N
 -> 摩擦錐の上限は 0.7 * 65 = 45 N        …足りる
 -> 必要な CoP 移動 = 13 * 0.3145 / 65 = 63 mm
 -> 横の CoP 箱は +-19 mm                 …3.3 倍足りない
```

制御周期は 5 ms なので 50 ms は 10 tick。**帯域は足りている。足りないのは、
その 50 ms で 13 N を作る権限で、それを止めているのは足裏の幅。**

今日ずっと「CoP 飽和は無害な run でも 1.00 で識別力なし」として退けてきた量が、
**識別量としてではなく権限の上限として**戻ってきた。§18.5 の判定(識別力なし)は
そのまま正しく、しかし別の役割で効いていた。

### 23.4 これが意味すること

- **制御アルゴリズムの問題ではない。** 必要な操作量が分かり、帯域も足り、
  摩擦も足りる。幾何で 3.3 倍足りない。
- 足裏を 38 → 46 mm(§21.7)は方向として正しいが **+21%**、3.3 倍には遠い。
- **50 ms 以内に権限を増やす唯一の手は支持多角形を広げること** = 早く足を着く。
  §21.5 の reduced-step 反射はそれを狙ったが効かなかった。

> **この段落は当初「短縮幅が 0.21 s までしかなく、50 ms の要求に対して 4 倍
> 遅かったから」と書いた。書いた直後に反証した(§23.6)。** 短縮幅を 0.210 →
> 0.035 s まで 6 段階振っても 4 点の結果は完全に同一。理由は別のところにある。

### 23.5 現在地

| 手 | 結果 |
|---|---|
| **ステップタイミング適応** | **有効**(+27 / -1、336 点) |
| 着地点補正 / `K_DCM` 引き下げ | 有害 |
| 角運動量タスク | 実装せず(ロール成分が原理的にゼロ) |
| reduced-step 反射 | 効果なし(理由は §23.6、短縮幅ではない) |
| 可変両足支持 | 制御量は動くが結果は変わらず |
| **介入実験** | **原因の所在を確定、壁を数値化** |

### 23.6 短縮幅は原因ではなかった(§23.4 の訂正)

`ADAPT_TIME_MIN` を 0.60 → 0.10(単脚支持の下限 0.210 → 0.035 s)まで 6 段階
振った:

```
MIN:        0.60    0.45    0.30    0.20    0.15    0.10
 (秒)      0.210   0.158   0.105   0.070   0.052   0.035
imp=0.20       X       X       X       X       X       X
imp=0.25       X       X       X       X       X       X
imp=0.65       .       .       .       .       .       .
imp=0.90       .       .       .       .       .       .
```

**6 列すべて完全同一。** 短縮幅は制約になっていない。

理由: 反射は **1 run につき 1 tick しか発火しない**。一度切るとそのスライスは
既に最短なので二度と条件を満たさず、短縮幅を変えても「最初の 1 回の切り方」が
変わるだけで以降の軌道は同じ。

**§23 の介入実験と条件が違っていたことにも注意。** あちらは `ADAPT_TIME=0`、
こちらは `ADAPT_TIME=1`。タイミング適応が先に位相を動かすので `Unreachable` に
落ちる状況が減り、棄却は 75 → 10 tick になる。そして `ADAPT_TIME=1` では
0.65 と 0.90 は既に生存している ── §23.2 の窓の表(`ADAPT_TIME=0`)と直接は
比べられない。**条件の違う実験の数字を並べていた。**

そして支持多角形を早く広げる経路は、これで閉じた。**遊脚を 35 ms で降ろしても
軌道が変わらないなら、§23.3 の 3.3 倍不足はこの手では埋まらない。**

残る幾何のレバーは足裏の幅だけ(§21.7 の 2 番、±19 → ±23 mm で +21%)。

## 24. 幾何を触ったら、制御 6 手ぶんを 1 手が超えた(2026-08-08)

  次の足の横オフセットを公称値より外側へ最大まで振る(ZMP デッド起点の
  `ADAPT_STEP` とは別物 ── 常に外側へ、内側へは動かさない)反射は未実装。

  下がっている方が測定効率が良い(§20.6 の運用方針そのもの)。

## 26. §25.4 の 3 候補を測った ── 2 つは実装まで進めて反証、1 つは保留(2026-08-08〜09)

### 26.1 `prox_weight` ── 効くが、綺麗な勝ちではない

`SolveConfig::default()` の `prox_weight: 0.0` を `PROX_WEIGHT` 環境変数化
(既定は 0.0 のまま、変更しない限り既存の測定は無効にならない)。42 ケースで
比較:

| | 42 ケース |
|---|---|
| `PROX_WEIGHT=0`(既定) | 34/42 |
| `PROX_WEIGHT=1e-4` | **37/42** |

ケース単位:

| ケース | 変化 |
|---|---|
| `vy=+0.055` / `vy=-0.055` | FELL → **SURVIVED** |
| `wz=+0.80` / `wz=-0.80` | FELL → **SURVIVED** |
| `vx=+0.109` | SURVIVED → **FELL** |

**純増 +3 だが、足裏幅(§24)のように全指標が揃って良くなる勝ちではない。**
横方向・旋回の 4 ケースを救う代わりに、速い前進 1 ケースを失う。

外乱ベンチ(14 セル×境界±4 点×反復 2、252 点/条件)を追加で測った。
**結果は明確に悪化。**

| 条件 | 生存(反復1/反復2、/252) |
|---|---|
| `PROX_WEIGHT=0`(既定) | 88 / 86 |
| `PROX_WEIGHT=1e-4` | **72 / 74** |

174 → 146、-28。ノイズ床(反復間差 0〜2 点)を大きく超える。CoP 縁滞在も
33 改善・50 悪化で同じ方向、`left ds`(4/9→1/9)・`right ss`(6/9→3/9)など
個別セルでも崩れが大きい。

**結論: 既定は変えない。** 42 ケースの +3(ケース単位で 1 悪化・4 改善)は
このセッションの主目的(外乱耐性)における -28(252 点)の悪化に対して
見合わない。`PROX_WEIGHT` 環境変数は残すが、既定は 0.0 のまま。

### 26.2 `joint_limit_cbf` ── 配線は直したが、ゲイン設計が想定より大きい

`misa_wbc::tasks::joint_limit_cbf` を torque box と同じレベル(`base`)に
追加(`JLIM`、既定 OFF)。実装時に一つ罠を踏んだ: `posture` タスクに合わせて
位置を `rig.robot.joint_positions` から読んだが、この配列は barn-in の
シード姿勢で凍結されたまま `BipedRig::new` 以降更新されない
(`posture` の位置項が定数ゼロなのはこれが理由で、そちらは無害だが、
バリアの「限界までの距離」には致命的)。`q`(misarta の生 state)を
`model.q_idx` 経由で読むよう修正。

修正後、均一な alpha ゲイン(1〜80 を掃引)で `EOM_HARD` の null-space
縮小と衝突し、レベル 1(torque box + 接触/摩擦錐 + joint limit)が
**即時 infeasible** になり 1 秒未満で転倒する。関節ごとの可動域が大きく違う
(hip_yaw ±30°、ankle_roll ±20°、膝 0〜130°)ため、単一ゲインでは狭い関節が
過剰ブレーキ・広い関節が無意味になる。関節ごとにスケールしたゲインが必要で、
これは当初の想定(設定値 1 つ)より大きい作業。**配線は残すが既定 OFF のまま
保留。**

### 26.3 `ADAPT_TIME_WIDE` ── 実装して測ったが、効果ゼロ

§25.4 で最有望とした候補。`StepTiming::Unreachable` をトリガに、次の着地点を
常に外側へ(内側には動かさない)固定量(既定 20 mm)ずらす反射
(`ADAPT_TIME_WIDE`、既定 OFF)。`ADAPT_TIME_CUT` とは独立フラグで、
1 step に 1 回だけ発火する(`last_wide_slice` ガード)。

14 セル×境界±4 点×反復 2(252 点/条件):

| 条件 | 生存(反復1) | 生存(反復2) |
|---|---|---|
| `timing off` | 88 | 86 |
| `timing on` | 103 | 102 |
| `timing cut` | 103 | 103 |
| **`timing wide`** | **103** | **103** |
| `timing cut+wide` | 102 | 102 |

**`safe`(セルごとの生存境界)は 14 セル全部で `timing on`/`cut`/`wide` が
小数点まで完全一致。** `cut` と同じく `wide` も何も変えていない。

原因を手動で確認した(`left ss (mirror)`、`PUSH_STEP=7`)。力積 0.20〜0.65 では
`Unreachable` が**一度も出ない**(0 solved / 0 declined)。0.90 まで上げて
初めて出る(4 solved / 68 declined)が、そこで widen は 1 step 発火して
なお転倒する。**`Unreachable` は §23.2 が「50 ms しか猶予が無い」と測った、
まさに手遅れの側でしか発火しない。** 猶予がある力積帯(0.20〜0.65)では
発火条件そのものが満たされないので、着地点をどれだけ外側へ振る仕掛けを
作っても届く先が無い。

**リアルタイムの脚配置調整という方向は、これで実質的に閉じた。** §23.1
(状態を外乱そのものより大きく補正しても最悪ケースの 3/4 は救えない)、
§22.3(制御量を目標帯へ完璧に入れても 4/4 転倒)、そしてこの §26.3
(唯一残っていた「タイミング+幅」の複合案も効果ゼロ)── 4 通りの独立な
実装(`ADAPT_STEP`・`ADAPT_DS`・`ADAPT_TIME_CUT`・`ADAPT_TIME_WIDE`)が
揃って同じ結論に達した。**残る本命は幾何(足裏幅、§24)だけ。**

## 27. パルス幅を振ったら、ベンチの前提そのものが崩れた(2026-08-09)

§21.7 の最後に残っていた 1 件。**「力積 [N·s] で刻めば幅は関係ない」という
§18.1 でのベンチの設計判断そのものが、今日まで検証されていなかった。**
検証したら崩れた。

### 27.1 やったこと

`scripts/kyo46rs_bench.py --push-dt-sweep`(新設)。各セルの力積を
`GRID_CENTRE`(境界値)に固定し、`PUSH_DT` だけを 0.05/0.10/0.15/0.20 s で
振る。`f = impulse / dt`(`kyo46rs_walk.rs`)なので、力積を固定したまま
パルスを短く・鋭くする。14 セル。

### 27.2 結果 ── 14 セル中 7 セルで、位相をまたがない 2 点だけでも反転する

生データは 14 セル中 12 セルで verdict が変わったが、そのうち何セルかは
`PUSH WARNING: pulse spills into the next support phase`(パルスが位相の
残り時間を超えて次の相に漏れる)が出ていた ── 「純粋な幅の効果」ではなく
別の現象が混ざっている。ログの `spill` 列で確認すると、**漏れが起きるのは
DS セルの 0.15/0.20 s と SS セルの 0.20 s のみ**で、0.05 s と 0.10 s は
14 セル全部で漏れゼロ(位相内に収まる)。

その漏れのない 2 点(0.05 s 対 0.10 s)だけで比較すると:

| セル | 0.05 s | 0.10 s |
|---|---|---|
| fwd ds | FELL | SURVIVED |
| back ds | FELL | SURVIVED |
| right ds | FELL | SURVIVED |
| back ss | FELL | SURVIVED |
| right ss | FELL | SURVIVED |
| diag ss | FELL | SURVIVED |
| left ss (mirror) | FELL | SURVIVED |
| left ds / diag ds / fwd ss / left ss /
  left ds(mirror) / right ds(mirror) / right ss(mirror) | 両方 SURVIVED | 同上 |

**14 セル中 7 セルで、同じ力積・同じ位相・漏れなしの 2 点だけで生死が
反転する。方向は 7 セル全部で同じ**(短い方が転倒、長い方が生存)。
偽陽性ではない ── 物理的にも筋が通る: 力積が同じでも短いパルスはピーク力が
高く、CoP・トルクの限界はピーク値に対して立つので、運動量が同じでも
「鋭い一発」は「ならした押し」より確実に厳しい。

### 27.3 これが意味すること

**この文書の「安全な力積は X N·s」という数値は、すべて暗黙の
`PUSH_DT=0.10 s` に紐づいている。** 力積だけでは転倒を決められない。

ただし**条件間の比較(タイミング適応・足裏幅など)は無傷。** どの比較も
`PUSH_DT` を条件間で揃えて測っているので、相対的な結論(§21・§24)は
崩れない。崩れるのは「この方向は何 N·s まで耐える」という絶対値の解釈で、
パルス形状を明示しない限り単体では意味を持たない。

再現: `python3 scripts/kyo46rs_bench.py --push-dt-sweep --csv csv/pushdt_sweep.csv`
(CSV の `spill` 列で位相漏れの有無を確認できる)。

|---|---|

## 29. 角運動量タスクを実装した ── 横歩きでは効かず、押しでは向きだけ揃う(2026-08-09)

§21.3 は角運動量タスクを**実装せずに反証**した。その根拠 2 本のうち 1 本
(「肩・肘とも矢状面軸なのでロール成分は原理的にゼロ」)は §28 の v6 肩ロールで
死んでいる。**残り 1 本(必要な `h_x` の大きさ)は死んでいない**が、そこは
「転倒とともに育った 1.10」と「単脚支持突入時の 0.178」のどちらを相手にするのか
が §21.3 では決まっていなかった。実装して測るしかない。実装した。

### 29.1 実装

`bt::angular_momentum`(`src/biped/tasks.rs`)── misarta の `A_G` と `Ȧ_G v` から
`ḣ_ang = -kp · h_ang` を要求する。**角行(0..3)だけを使う**: 線形行
`h_lin = m·ṗ_com` は CoM タスクの変数そのもので、2 つのレベルに同じ量を
要求させても「どちらが負けるか」が決まるだけ。

`kyo46rs_walk.rs` 側の env: `MOM`(既定 OFF)、`KP_MOM`、`MOM_AXES`
(roll/pitch/yaw の 3 文字マスク、既定 `x--`)、`MOM_LEVEL`。

### 29.2 効くかどうかを決めるのはゲインではなく**階層内の位置**

まず素直に「swing の下・posture の上」に置いてゲインを振った。全滅する:

| `KP_MOM` | safe | 生存 |
|---|---|---|
| off | 0.018 | 12/28 |
| 1 | 0.000 | **0/28** |
| 3 | 0.000 | **0/28** |
| 10 | 0.000 | **0/28** |
| 30 | 0.000 | **0/28** |

**`kp=1` でも全滅する**ところが答えになっている。このタスクはそのレベルでの
**等式**なので、`kp` が小さくても要求は消えない ── `kp=0` ですら
「`ḣ_ang = 0`、つまりロール角運動量を決して変えるな」を要求し続ける。
歩行はそれを満たせない。**`kp` はタスクの強さを決めていない。**

強さを決めているのは配置なので、配置を振った:

| 配置 | safe | 生存 | 自己干渉(中央値) |
|---|---|---|---|
| off | 0.018 | 12/28 | 178 |
| swing の上(`swing_before/after`) | 0.000 | **0/28** | 493〜632 |
| posture の下(`post_after`) | 0.018 | **12/28** | 203 |
| posture と**同一レベル**(`post_merge`) | 0.000〜0.018 | **10〜11/28** | 179〜200 |

**上に置けば歩行を食い潰し、下に置けば完全に不活性、同居させても変わらない。**
`post_after` は kp=3 でも kp=30 でも `off` とセル単位で一致する ── null space が
残っていないので、何を要求しても出力に届かない。`post_merge` は 10〜11/28 で、
`off` の 12/28 に対して**まだら幅の中**(§18.2)。3 軸全部(`xyz`)にしても 13/28 で
同じ範囲。

### 29.3 外乱ベンチ ── §21.3 が本当に主張していた土俵で測ると、話が変わる

§29.2 は**横歩き**の梯子で、§21.3 の主張は**押しに耐えるか**だった。別物なので
押しベンチでも測った(`mom off` / `mom merge k10` を `PUSH_CONDITIONS` に追加、
左右 8 セル × 境界±4 点 × 反復 3 = 432 run):

| | 生存(216 中) | セル単位の向き |
|---|---|---|
| `mom off` | 145 | ─ |
| `mom merge k10` | **153** | **8 セル中 7 セルで改善**(+1,+1,+1,+2,+3,+1,+1、悪化 -2 が 1 セル) |

CoP 縁滞在は 7 点改善・9 点悪化で**動かない。**

**これは「効いた」と書ける結果ではない。** 各セルの改善幅 1〜3 点は、そのセル
自身のばらつき(最悪 3 点)の中に収まっている ── ベンチ自身が
「1 セルでこれ以下の差は測定ではない」と印刷している通り。意味があるとすれば
**8 セル中 7 セルで向きが揃っていること**の方で、これは 1 セルの大きさとは
別の情報。ただしコイン投げでも 8 回中 7 回同じ向きは珍しくない(両側 p≈0.07)。

**未確定として記録する。** 決着させるなら反復を 3 → 10 に上げて同じ 8 セルを
測り直すこと。今日の 432 run で 47 分なので、反復 10 なら約 2.5 時間。

横歩きでは無効〜有害、押しでは弱く改善の向き ── **同じタスクが 2 つのベンチで
違う符号を出している**ので、どちらか一方だけを見て既定を決めてはいけない。
既定は OFF のまま。

### 29.4 これが意味すること

**厳密階層(HoQP)の WBC では、このタスクは「弱く効かせる」ことができない。**
効くか、全部持っていくかの二値で、その間に連続的なつまみが無い。§21.3 は
「腕の角運動量が足りない」と論じたが、実測は**足りる/足りない以前に、
このタスクをこの階層に置く場所が無い**と言っている。

したがって §21.3 の結論(実装しないでよい)は**今日の測定でも覆っていないが、
理由は書かれていたものと違う。** 印を付けておく。ただし §29.3 の押しベンチは
弱い改善の向きを見せているので、「反証済み」ではなく**「横歩きでは無効、
押しでは未確定」**が今日時点の正確な状態。

残る筋があるとすれば、等式ではなく**不等式**(`|h_x| ≤ 上限` の CBF 型)にして
「普段は何も要求せず、閾値を超えたときだけ効く」形にすること。今の
`centroidal_momentum` は `cartesian_acceleration` そのままなので、これは
misa-wbc 側の新しいタスクになる。**未着手。**
