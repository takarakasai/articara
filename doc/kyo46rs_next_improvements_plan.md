# kyo46rs 次の改善計画

- 作成日: 2026-08-09
- 前提: `doc/kyo46rs_biped_wbc.md` §0-27 の測定結果。個々の根拠は本文に
  `§n` で示す。ここは測定ログではなく、そこから導いた**次の実装判断**をまとめる
  計画書。
- 優先順位(投資対効果):
  1. メカ①(hip_roll RS00 単体交換 + hip_pitch 単発化) ── **実装済み(v4/v5)**
  2. メカ③(肩ロール追加) ── **メカ側実装済み(v6)、制御側は未着手**
  3. 制御(`joint_limit_cbf` のゲイン設計 + degraded 解の根本原因)
  4. 計画(前進速度の壁の直接測定)
  5. メカ②(腰関節・胴体質量)は**変更なし**が結論、MPC/RL は探索的・低優先
- `kyo46rs_description` 側の実装コミット: `1d32b17`/`79f5afd`(knee, v3)、
  `a9298c9`(hip_roll, v4)、`839d69c`(hip_pitch 撤去 v5 + shoulder_roll v6)。
  現行総質量 6.338 kg(v1比 +0.776 kg、v2比 -0.292 kg)。

## 1. メカ構成① ── 脚の自由度配置・関節配置

### 1.1 hip_roll ── EL05 を RS00 に置き換える(単体交換) ── **実装済み(2026-08-09)**

`kyo46rs_description` 側で実施済み(`kyo46rs.urdf` v4、コミット `a9298c9`)。
経緯の記録: RS00 は EL05 の別名ではなく別モデルで、当初「knee は元から
RS00(2基)」と考えたがそれも古い設計で、実際は**knee 自体を RS00 1基に
一本化**(v3、コミット `79f5afd`)した上で、**hip_roll も同じ「ブースタでは
なく単体交換」を適用**(v4)。RS00 の実仕様(ユーザ提供 2026-08-09):

| Robstride RS00 | value |
|---|---|
| 質量 | 0.310 kg |
| 連続トルク | 5.0 N·m |
| ピークトルク | 14.0 N·m |
| 寸法 | 57×57×51 mm |
| ギア比 | 10:1 |
| 無負荷回転数 | 315 rpm(33.0 rad/s) |

**根拠**: §10.11、片足支持中の hip_roll トルクが EL05 連続定格 1.8 N·m の
253%(実測 4.56 N·m、ピーク比 76%)。W1(重み移動)の実際の壁であり、§25 の
立脚幅掃引が指標間で割れた原因(幅を変えると hip_roll のモーメントアームも
一緒に変わる)でもある。

**実施内容**: `left/right_hip_roll_joint` の `effort` を 6.0→**14.0 N·m**、
`velocity` を 10.0→**33.0 rad/s** に、`left/right_hip_roll_link` 質量を
0.252→**0.320 kg** に変更(ベルト・遠隔配置は不要 ── hip_roll は元から
単一モータなので、そのまま置き換えるだけ)。総質量 6.222→**6.358 kg**。

**結果**: 4.56 N·m は RS00 単体のピーク 14.0 N·m の **33%**(EL05 ピークの
76% から改善)。連続定格でも 4.56/5.0 = **91%**(EL05 の 253% から大幅改善)。
**ただし連続定格91%はまだ薄い** ── 片足支持を長く維持する用途では要注意、
という留保付きで README に明記済み。

**未検証のまま残るもの**(次のアクション):

- **寸法干渉**: 46×46×44mm→57×57×51mmへの寸法増が実際に収まるか
  (`kyo46rs_selfcollision_check`)。README の hip 周りの梱包は「30mm の
  名目オフセットで模式的に詰めている、検証済みの機械梱包ではない」と
  明記されている。
- **連続定格91%の実運用確認**: §10.11と同じ片足支持トルク実測を、新しい
  URDF(v4)に対して再実行。91%が実際に問題になるなら、knee(v3以前)と
  同型の「RS00 2基・近位+ベルト」のブースタ方式へ切り替えるフォールバックが
  README に記載済み(連続定格を 46% まで緩められる)。
- **articara 側の制御コード変更は不要** ── `CtrlMode` は対象アクチュエータが
  増えるだけで、knee で RS00 を既に使っているため新規プロトコル対応もない。

### 1.2 hip_pitch の第 2 モータを外す ── **実装済み(2026-08-09、v5)**

`kyo46rs_description` 側で実施済み(`kyo46rs.urdf` v5、コミット `839d69c`)。

**根拠**: §6 で全負荷ケースにおいて不要と判定済み(最悪でも連続定格の93%)。
§17.3 で「トルクを 12→6 N·m に半減しても 5 件中 4 件が完全一致」と
**独立した機体(kyo46rs2)で再確認**済み。

**実施内容**: `left/right_hip_pitch_joint` の `effort` を 12.0→**6.0 N·m**
(単一 EL05 に戻す)、`torso` 質量を 1.274→**0.75 kg**(ブースタ2基+
ブラケットを削除、v2以前の元の値に戻る)。総質量 6.358→**5.834 kg**
(この時点。直後に §3.1 の肩ロール追加で 6.338 kg になる)。

### 1.3 やらないこと

- **ankle_roll の ROM 拡張** ── §16.4・§18.5 で 2 回、ROM を ±20°→±40° に
  広げても限界も天井も動かないと確認済み。飽和は結果であって原因ではない。

## 2. メカ構成② ── 上半身(体幹関節)

**結論: 現状維持。** §12.3 で yaw/roll/pitch の 3 種の腰関節を実装して比較
済み。yaw はわずかに有利(DCM 誤差 12.7→10.2 mm)だが、追加アクチュエータ
1 基と degraded 35→93 の代償に見合わず、yaw の問題自体はソフト側
(トランク yaw タスク + 遊脚 yaw 軸)で既に解決している。roll/pitch は
悪化(ただし現行制御則が専用タスクを持たないという条件付き ── 将来 pelvis
leveling タスクを書くなら再評価の余地はあるが、優先度は低い)。

**質量配分は変更の価値がある。** §17.5: 胴体質量を 41% 軽くしただけで
後退・横移動の余裕が失われた(遊脚を振った反作用を受け止める役目)。
**胴体の軽量化は避け、バッテリ・基板等の質量は脚・腕より胴体側に置く**方針。
胴体重心の高さは無関係(§17.5 で確認済み)。

## 3. メカ構成③ ── 上半身(腕・首)

### 3.1 肩に外転(roll)自由度を追加 ── **メカ側は実装済み(2026-08-09、v6)、制御側は未着手**

`kyo46rs_description` 側で実施済み(`kyo46rs.urdf` v6、コミット `839d69c`)。
`left/right_shoulder_roll_joint`(EL05、`effort` 6.0 N·m、可動域は左右
ミラーで -10°〜90°/-90°〜10°、torso→roll→pitch→upper_arm の順、この
URDF 自身の hip_yaw→hip_roll→hip_pitch と同じ並び)。総質量 5.834→
**6.338 kg**。自己干渉チェック(`kyo46rs_selfcollision_check`)はクロウチ
姿勢で接触ゼロを確認済み。

**根拠 ── 二重に効く**:

1. §10.4: 前腕⇔股関節ブロックの自己干渉(隙間 2.5 mm)。回避には
   `ARM_PITCH=-1.40`(腕をほぼ水平前方)という不自然な姿勢が必要で、
   これ自体が重心を 16 mm 前へ動かし LIPM の前提を乱す。
2. §21.3: 角運動量タスクを実装前に反証した理由が「肩・肘とも矢状面軸で
   ロール成分が原理的にゼロ」。肩ロールを足せば**自己干渉問題と閉じていた
   制御レバー(腕振りバランス戦略)が同時に開く。**

**制御側は未着手 ── 次のアクション**: 関節を追加しただけでは何も変わらない
ことを確認済み(`ARM_PITCH=0` で歩かせると self-collision 748 tick ── 追加前の
301 tick より増えている。P4 姿勢保持タスクが値をシード姿勢近辺に置くだけで、
外転方向へは何も指令していないため)。

1. 姿勢シード(`q_seed`)で `shoulder_roll` に外転バイアスをかけ、
   `ARM_PITCH=-1.40` のような不自然な pitch 姿勢を使わずに自己干渉ゼロを
   再確認する(まず一番簡単な検証)。
2. 角運動量タスク(`misa-wbc` の `centroidal_momentum`)を実際に配線して
   §21.3 で見積もった 1.10 kg·m²/s 規模の外乱で効果を測る。

### 3.2 首・頭部

**この文書では一度も検討されていない。** 腕がバランスレバーとして使えない
(質量・モーメントアームが小さい)のと同じ理由で、首単体がバランスに効く
可能性は低い。視線安定化など別目的でなければ**優先度は低い**まま。

## 4. 制御(WBC・MPC・RL)

### 4.1 `joint_limit_cbf` の関節別ゲイン設計(§26.2 で保留中、優先度高)

**根拠**: ankle_roll が限界を超える事象が、外乱ベンチ(§18.5, 196%)だけでなく
歩行の別の文脈でも繰り返し出ている ── §11.6(151%)、§16(141〜201%)。
単発の偶然ではなく構造的な穴。§26.2 で均一ゲインが `EOM_HARD` の
null-space 縮小と衝突して即時 infeasible になると判明済みなので、
関節ごとにスケールしたゲイン(可動域・想定角速度から逆算)が必要。

### 4.2 degraded 解が最下段に集中する問題の根本原因

**根拠**: §11.6 で「degraded 231、全て最下段(regularise)」を「正常ではない」
と記録したまま未追跡。§14.5 で `k_dcm` を下げると degraded が 559→7206 に
爆発する現象と根が同じ可能性が高く、`prox_weight` のコールドスタート問題
(§26.1)とも合わせて調べる価値がある。**これが解決すると§4.3の速度向上策
がノーコストで採用可能になる**(下記 5.2)。

### 4.3 MPC

**外乱耐性の目的では優先度低い。** §23.3 の壁(最悪ケースは 50 ms しか
猶予がない)は MPC の計算遅延より短く、§26.3 で 4 つの独立した機構が
「実時間の脚配置・タイミング調整には権限が残っていない」と結論している。

**前進速度の壁(§16.5、未解決)には好適。** 反射的対応ではなく定常軌道の
実現可能性の問題なので、計算に時間をかけられる MPC・長ホライズン計画が
向いている(下記 5.1)。

### 4.4 RL

**試されたことが一度もない、正真正銘の新しい方向。** 既存のベンチ量
(CoP 縁滞在率・生存数・DCM 誤差)は報酬設計にそのまま転用できる。
**ただし§23の時間予算の壁は制御則の種類を問わない** ── RL で狙うべきは
猶予がある 0.20〜0.65 N·s 帯に限定し、0.90 N·s 以上を「学習で解決する」
という期待は今回の測定と矛盾する。

## 5. 計画(脚配置計画)

### 5.1 前進速度の壁を直接測る(優先度高、唯一の未解決の壁)

**根拠**: §16.5「前進の壁(0.109 OK / 0.145 転倒)はこの修正で動かない…
§14 からの宿題として残る」と明記されたまま、この文書内で専用の追跡調査が
一度も行われていない。§4(片足支持)・§10.11(hip_roll)を崩したのと同じ
「実際に何が飽和しているかを直接測る」手順(トルク・CoP箱・遊脚速度・
膝ROM を個別に固定/緩めて切り分ける)が未適用。

**次のアクション**: 0.109→0.145 の間で転倒直前の関節トルク・CoP 箱使用率・
遊脚軌道速度・DCM 誤差を tick 単位で記録し、§4.1 のように「何が実際に
飽和しているか」を数値で確定する。

### 5.2 capture point 型足配置計画(§14.3〜14.5、既に効果実測済み、既定 OFF)

**根拠**: `k_dcm` を下げてから連続的に DCM 基準を再構築すると、
stride=0.06 の壁が 26 歩→132 歩に伸びる(§14.5)。既定 OFF の理由は
低 `k_dcm` で degraded 解が 559→7206 に爆発すること。

**次のアクション**: 4.2(degraded 解の根本原因)が解決すれば、この速度向上策を
コストなしで既定化できる可能性がある。4.2 の後回しにせず並行して当たる
価値がある。

### 5.3 外乱への反応的な足配置

**これで打ち止め。** §26.3 で `ADAPT_STEP`・`ADAPT_DS`・`ADAPT_TIME_CUT`・
`ADAPT_TIME_WIDE` の 4 通りが揃って無効/有害と確定済み。戻る理由はない。

### 5.4 旋回

**既に解決済み、追加作業不要。** §16 で座標系バグを修正し 0.60〜1.00 rad/s
まで生存。壁は「一歩あたり約 19°」で旋回レートではないことも判明ずみ
(§16.3)── 今後の歩容設計では歩調と一歩あたりの旋回量のトレードオフとして
覚えておく定数。
