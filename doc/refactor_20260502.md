# Refactor 2026-05-02: ネイティブマスタ形式 `.misa` の導入

## 1. 背景と目的

articara は現在、ロボットモデルを **URDF / SDF / MJCF / USD** の4形式で
import / export できるが、編集・動力学シミュレーションにおける
「マスタ形式」が定まっていなかった。

実態としては:

- 内部表現: `RobotModel` (`src/rbd/model.rs`) と misarta の `Model` に
  キャッシュされる
- 永続化: 主たる本体ファイルは URDF、それでは表現できない情報
  (loop_closure, mimic, sensor, pose, sequence, actuator, gait, home)
  は `.misarta.toml` サイドカーに退避

この構成では:

- URDF にできない要素を扱うたびに二重管理が発生する
- どの形式を「正」とするかが各機能で曖昧
- 動力学シムや組み込み配信で、URDF + サイドカーの2ファイル運用が前提となる

これを整理するため、**articara/misarta ネイティブの単一マスタ形式**を
新設し、外部4形式は派生エクスポート/インポート扱いに位置付け直す。

---

## 2. 決定事項サマリ

| 項目 | 決定 |
|---|---|
| マスタ形式 | 独自フォーマット(中身は TOML) |
| 拡張子 | **`.misa`** |
| ファイル先頭の識別 | `schema = "misarta/1"` を**必須** |
| パーサ配置 | **misarta クレート**(pinocchio パターン踏襲) |
| 新モジュール名 | `misarta::native` |
| 構造表現 | フラット(URDF型 + parent/child 参照) |
| 姿勢表現 | rpy 既定、quat 許可(loop_closure 等は quat 必須) |
| ジオメトリ寸法 | URDF流の全サイズ(`size = [w, h, d]`、`length` は全長) |
| メッシュ | 常に外部参照、`meshes/` サブディレクトリ前提、埋め込み無し |
| マテリアル | インライン色既定、`[[material]]` 名前参照は任意 |
| 識別子規約 | `^[A-Za-z_][A-Za-z0-9_]*$`、違反は自動 sanitize + ダイアログ提示 |
| Actuator-Joint | N:M 表現可能(`[[actuator]] joints = [...]`)、物理特性は `[[joint]].dynamics` に分離 |
| 既存 `.misarta.toml` | namiashi 1ファイルのみ → 完全置換、互換コードは入れない |
| 標準エクスポート | 引き続き URDF / MJCF / SDF / USD をサポート |

## 3. アーキテクチャ

### 3.1 3層構成

ファイルシステム依存を疎結合化し、組み込み・WASM 移植性を確保する。

```
┌─────────────────────────────────────────────────────────┐
│ Layer 3: 利便性 API(std + fs 必須)                      │
│   misarta::native::load(path) -> ParseOutput            │
│   misarta::native::save(path, ...) -> Result            │
└──────────────────────┬──────────────────────────────────┘
                       │
┌──────────────────────▼──────────────────────────────────┐
│ Layer 2: コアパーサ(std 必須だが fs 非依存)              │
│   misarta::native::parse_str(text, &dyn AssetSource)    │
│     -> ParseOutput                                      │
│   ※ メッシュ参照は AssetSource 経由で解決                │
└──────────────────────┬──────────────────────────────────┘
                       │
┌──────────────────────▼──────────────────────────────────┐
│ Layer 1: 抽象化トレイト(fs 非依存)                       │
│   trait AssetSource {                                   │
│     fn read(&self, path: &str) -> Result<Vec<u8>>;      │
│     fn exists(&self, path: &str) -> bool;               │
│   }                                                     │
└─────────────────────────────────────────────────────────┘
```

### 3.2 AssetSource 実装

```rust
pub trait AssetSource {
    fn read(&self, path: &str) -> Result<Vec<u8>, AssetError>;
    fn exists(&self, path: &str) -> bool;
}

pub struct FileSystemSource { root: PathBuf }
pub struct InMemorySource   { files: BTreeMap<String, Vec<u8>> }
pub struct StaticBundleSource<'a> { files: &'a [(&'a str, &'a [u8])] }
pub struct NullSource;  // メッシュ要求はエラー
```

### 3.3 メッシュロードのタイミング

ハイブリッド方式(構造解析とメッシュ展開を分離):

```rust
let mut out = parse_str(text, &assets)?;       // 構造のみ
out.load_meshes(&assets)?;                     // 任意: 視覚メッシュ
out.load_collision_meshes(&assets)?;           // 任意: 衝突メッシュ
```

組み込みノードで動力学計算のみ行いたい場合、メッシュデータを
線形メモリに乗せずに済む。

### 3.4 ジェネリクス vs 動的ディスパッチ

`AssetSource` は **`&dyn AssetSource`** で受け取る。
モノモーフィゼーション抑制で組み込みのバイナリサイズを抑える。
デスクトップ性能への影響は無視できる。

### 3.5 パスサニタイズ要件

`AssetSource` 実装は path traversal 対策を必須とする:

- 絶対パス(`/`, `\`, ドライブレター)拒否
- `..` を含むパス拒否
- `FileSystemSource` は root 配下に正規化されたことを `starts_with` で再検証

これは **トレイトのドキュメント要件**として明記する。

### 3.6 ParseOutput とサニタイズレポート

```rust
pub struct ParseOutput {
    pub model: Model<f64>,
    pub geometry: GeometryModel,
    pub config: MisartaConfig,
    pub report: LoadReport,
}

pub struct LoadReport {
    pub sanitized_names: Vec<NameSanitization>,
    pub material_collisions: Vec<MaterialCollision>,
    pub missing_meshes: Vec<String>,
    pub warnings: Vec<String>,
}

pub struct NameSanitization {
    pub category: String,        // "link", "joint", "material", ...
    pub original: String,
    pub sanitized: String,
    pub reason: String,          // "contained '-'", "started with digit"
    pub occurrence_index: usize,
}

pub struct MaterialCollision {
    pub original: String,
    pub renamed_to: String,
}
```

articara 側は `report.is_empty()` でない時に egui ダイアログで
**全項目を一覧表示**する(ユーザに変更を可視化)。

## 4. スキーマ草案 (`schema = "misarta/1"`)

### 4.1 トップレベル構成

```toml
schema = "misarta/1"

[robot]
name = "namiashi"
root = "trunk"

# ── 共有アセット(任意) ──
[[material]]

# ── 運動学 / ジオメトリ ──
[[link]]
[[joint]]

# ── 多体制約 / 物理拡張 ──
[[mimic]]
[[loop_closure]]
[[collision_pair]]
[[sensor]]

# ── 制御 ──
[[actuator]]   # N:M 対応、独立テーブル

# ── シム / 編集メタ ──
[[pose]]
[[sequence]]
[[gait]]
[home]
```

単位は **m / kg / rad / s 固定**(暗黙)、軸規約は **Z-up 固定**(暗黙)。

### 4.2 リンク

```toml
[[link]]
name = "trunk"
description = "胴体。バッテリーとIMUを内蔵"   # 任意

inertial = { mass = 5.0, ixx = 0.10, iyy = 0.10, izz = 0.10,
             ixy = 0.0, ixz = 0.0, iyz = 0.0,
             origin = { xyz = [0, 0, 0.05], rpy = [0, 0, 0] } }

[[link.visual]]
origin = { xyz = [0, 0, 0], rpy = [0, 0, 0] }
geom   = { box = { size = [0.30, 0.20, 0.10] } }
color  = "#cc6644"

[[link.visual]]
origin = { xyz = [0.10, 0, 0.05], rpy = [0, 1.5708, 0] }
geom   = { mesh = { file = "meshes/trunk_decoration.stl",
                    scale = [1, 1, 1] } }
material = "red_plastic"   # インライン color の代わりに名前参照も可

[[link.collision]]
origin = { xyz = [0, 0, 0], rpy = [0, 0, 0] }
geom   = { capsule = { radius = 0.04, length = 0.20 } }
```

`geom` のタグ:
- `box`     — `size = [w, h, d]`
- `cylinder`— `radius`, `length`
- `sphere`  — `radius`
- `capsule` — `radius`, `length`(円筒部分の長さ。総長 = length + 2*radius)
- `mesh`    — `file`, `scale`

### 4.3 ジョイント(物理特性のみ)

```toml
[[joint]]
name   = "hip_pitch"
type   = "revolute"          # revolute / continuous / prismatic / fixed / floating / planar
parent = "trunk"
child  = "thigh"
axis   = [0, 1, 0]
origin = { xyz = [0.05, 0.10, 0], rpy = [0, 0, 0] }
limit  = { lower = -1.5708, upper = 1.5708, effort = 30.0, velocity = 10.0 }

# 受動物理特性: ベアリング摩擦・ロータ慣性。アクチュエータ有無に独立
dynamics = { armature = 0.0014, damping = 0.10 }
```

### 4.4 アクチュエータ(N:M 対応、別テーブル)

```toml
# 1:1 (普通のサーボ)
[[actuator]]
name   = "hip_pitch_motor"
mode   = "Position"
joints = [{ name = "hip_pitch", gear = 1.0 }]
kp = 100.0
kv = 1.2

# N:1 (差動)
[[actuator]]
name   = "diff_drive_a"
mode   = "Torque"
joints = [
  { name = "wheel_left",  gear =  1.0 },
  { name = "wheel_right", gear = -1.0 },
]

# 1:N (テンドン/ケーブル駆動)
[[actuator]]
name   = "finger_tendon"
mode   = "Position"
joints = [
  { name = "finger_mcp", gear = 1.0 },
  { name = "finger_pip", gear = 0.7 },
  { name = "finger_dip", gear = 0.5 },
]
kp = 50.0
kv = 0.5
```

`mode`: `Position` / `Velocity` / `Torque` / `ComputedTorque`
`gear`: 線形カップリング係数(MJCF `gear`、tendon `coef` 相当)

**Mimic との違い**: `[[mimic]]` は運動学的拘束(同一自由度として扱う)、
`[[actuator]] joints=[...]` は制御入力の分配(独立自由度のまま1コマンドで動かす)。

### 4.5 物理拡張テーブル

```toml
[[mimic]]

multiplier = -1.0
offset = 0.0
```

## 5. ファイル配置

```
robots/namiashi/
├── namiashi.misa            # マスタ
└── meshes/
    ├── trunk.stl
    ├── thigh.stl
    └── ...
```

- メッシュ参照は **マスタファイル相対**(`file = "meshes/trunk.stl"`)
- 絶対パス・`..` は禁止
- URDF の `package://...` は import 時に相対パスへ正規化
- procedural mesh はエクスポート時に `meshes/` 配下に自動 STL 生成

## 6. 識別子規約

全エンティティ名(link / joint / material / sensor / pose / sequence /
actuator / mimic / loop_closure)に共通:

```
^[A-Za-z_][A-Za-z0-9_]*$
```

理由:

- USD prim path 制約に整合
- ROS topic name 規約に整合
- 既存サンプル(`FL_calf_joint`, `arm_pitch_joint`)は全て適合

違反検出時:

- `-` → `_` 置換
- 空白除去
- 先頭が数字 → `_` プレフィックス付与
- 衝突したら末尾に `_2`, `_3` ...

すべての置換を `LoadReport.sanitized_names` に記録 → ダイアログで一覧提示。

## 7. パーサの責務分担

### 7.1 misarta::native の責務

- `.misa` ファイルの構造的パース(TOML → 中間 AST)
- `Model` / `GeometryModel` / `MisartaConfig` への変換
- 識別子サニタイズと LoadReport 生成
- メッシュ参照の AssetSource 経由解決(任意)
- 書き出し(save 関数)

### 7.2 articara の責務

- `RobotModel::from_misa(path)` で `misarta::native::load` を呼び出し
- LoadReport を egui ダイアログで表示
- `VisualData.color` (f32×4) など articara 固有の表示属性をマッピング
- GUI / undo / 編集状態の管理

### 7.3 既存実装との関係

| 形式 | 現状の実装位置 | 将来的な整理(別タスク) |
|---|---|---|
| URDF | `misarta::urdf` | そのまま、AssetSource 対応は後追い検討 |
| SDF  | `misarta::sdf` と `articara::sdf` の二重実装 | misarta 側に統合 |
| MJCF | `articara::mjcf` のみ | misarta に移動検討 |
| USD  | `articara::usd` / `articara::usd_import` のみ | misarta に移動検討(USD依存方針による) |
| `.misa` | **新設: `misarta::native`** | — |

## 10. リスクと対応

| リスク | 緩和策 |
|---|---|
| `.misa` を読めるツールが articara/misarta だけ | URDF/MJCF/SDF/USD への lossy export を維持。マスタは独自でも、外部公開時は標準形式に変換可能 |
| 拡張子 `.misa` の認知度ゼロ | `schema = "misarta/1"` ヘッダで自己説明、README で明記 |
| TOML がツリー構造に弱い | フラット表現 + parent/child 参照で回避(URDF と同パターン) |
| メッシュサニタイズが Layer 1 トレイト要件 → 実装者が遵守しないとセキュリティ問題 | 主要実装(FileSystemSource)で正規化、トレイトドキュメントで明示要求 |
| no_std 化を最初に諦めると後でやりづらい | トレイト境界・依存関係は no_std 互換に揃えておく(現状は feature gate のみ) |

---

## 11. 議論の経緯(参考)

決定の経緯を要約すると:

1. **マスタ候補比較**: URDF / SDF / MJCF / USD / `.misarta.toml` 拡張 /
   独自フォーマットを比較。表現力では MJCF が最強だが、
   articara 固有メタ(pose, gait 等)を完全に保存するには独自形式が必要。
2. **独自形式に決定**: 「マスタは独自、外部4形式は派生エクスポート」で
   独自形式の表現力と外部互換性を両立。
3. **形式選定**: TOML / YAML / KDL / RON / JSON5 を比較。
   既存 `misarta::config` が TOML、Rust エコシステムでの安定性
   (`serde_yaml` の保守停止)、フラット表現との相性で **TOML 採用**。
4. **拡張子・モジュール命名**: パーサ責務を持つ misarta にちなんで
   `.misa` / `misarta::native`。
5. **Actuator-Joint カーディナリティ問題**: 当初「joint 内インライン」案
   だったが、N:M 機構(差動・テンドン)を扱えないため独立テーブル化。
   armature/damping は物理特性なので joint 側に分離。
6. **組み込み配信を見据えた疎結合化**: pinocchio パターンに倣い
   `AssetSource` トレイトでファイルシステムを抽象化、3層構造に。
   no_std は将来課題として現状は std 必須で開始。
