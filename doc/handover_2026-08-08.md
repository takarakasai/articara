### 壁の数値(§23.3)

最悪ケースを救うには **押されてから 50 ms 以内に重心速度 0.10 m/s** が要る。

```
0.66 N*s / 50 ms = 13 N の水平力
  摩擦錐の上限 0.7 * 65 = 45 N          …足りる
  必要な CoP 移動 13 * 0.3145 / 65 = 63 mm
  横の CoP 箱 ±19 mm                    …3.3 倍足りない
```

制御周期 5 ms なので帯域は足りている。**足りないのは権限で、止めているのは足の幅。**

## 3. 手順のルール(これがいちばん持ち出す価値がある)

このセッションは**測定を 6 回間違えた**。原因と対策:

1. **単一セルの結果は仮説生成にのみ使う。** 1 セル 24 点の生存数は、摩擦係数を
   1e-7 相対で動かすだけで **±2 振れる**(§20.4)。3 run で結論を出して 2 回、
   24 点で 4 回、判断を誤った。**結論は 14 セル合計(±7)で述べる。**
2. **新しい比較を始める前にノイズ床を測る。** `--repeat N` がそのためにある。
   格子を境界 ±4 点に絞ると床が ±2 → 0〜3 に下がり、3 倍効率が良い。
3. **既定歩容の対照を必ず取る。** `ADAPT_TIME` は最初、外乱ゼロでも毎 tick
   再計時して 42 ケースを 34 → 26 に落とした。ゲート(`ADAPT_TIME_TRIG`)で
   34/42 にケース単位で完全復帰。
4. **分離量を見つけて動かす、をやってはいけない。** 6 個見つけ、動かせた 3 個は
   どれも結果を変えなかった(§22.5)。転倒に向かう軌道はあらゆる量で正常軌道から
   離れるので、分離は原因を特定しない。**代わりに介入する**(§23、`FIX_DV` /
   `FIX_TAU` / `FIX_AT_S`)── 72 run で「コミット時点に原因は無い」と切れた。
5. **`pgrep -f` は自分のコマンド文字列にマッチする。** 「まだ動いている」と 2 回
   誤報した。`ps` で裏を取ること。
6. **取り下げは節の見出しだけでなく該当段落にも印を付ける。** 外部レビューの
   1 系統が、取り下げ済みの説を根拠に使ってきた(§21.8)。

## 4. ベンチの使い方

```bash
# 単発(押しは env、詳細は doc §18.1 に再現コマンド)
T_SS=0.35 T_DS=0.20 STRIDE_RAMP=6 ARM_PITCH=0 LIFT_H=0.02 PHASE_BY_CONTACT=0 \
N_STEPS=20 T=15.0 VX=0.055 ADAPT_STEP=0 K_DCM=2.0 FIRST_SWING=0 \
PUSH_DEG=90 PUSH_STEP=6 PUSH_AT=0.5 PUSH_SUPPORT=ss PUSH_IMPULSE=0.20 \
TRAJ_CSV=csv/x.csv ./target/release/examples/kyo46rs_walk

# 条件比較(必ずこの形。格子は条件間で同一、セル間だけ中心が違う)
python3 scripts/kyo46rs_bench.py --push-sweep \
  --push-conditions "sole 38,sole 46,sole 60" \
  --grid-around --grid-half 4 --grid-step 0.05 --repeat 2 --csv csv/out.csv

# 外乱なしの対照(必須)
python3 scripts/kyo46rs_bench.py            # 34/42 が現行の基準値

# 動画(矢印つき)
TAU_JOINTS="left_hip_roll_joint:L_hip_roll,right_hip_roll_joint:R_hip_roll,left_ankle_roll_joint:L_ankle_roll" \
PUSH_IMPULSE_LABEL=1.20 python3 examples/render_com_squat_video.py csv/x.csv videos/x.mp4
```

`PUSH_*` / `ADAPT_TIME*` / `ADAPT_DS*` / `FIX_*` / `SOLE_HALF_W` はすべて
`examples/kyo46rs_walk.rs` の冒頭に定義とコメントがある。

判定量は **CoP 縁滞在**(単脚支持突入後 100 ms、立脚 CoP が足裏の縁にいた割合)。
ただし**突入時刻を動かす介入(タイミング系)には向かない** ── 2 歩目でも測るように
してあるので両方見ること(§21.4)。

## 5. 次にやること(優先順)

1. **立脚幅の掃引** ── 幾何で唯一残っている軸。99.4 mm は §10.11 で hip_roll
   トルク基準で決めた値で、今日の指標では測り直していない。DS の横余裕は幅と
   ともに増えるので、トレードオフの向きが変わっている可能性。URDF の hip_yaw
   原点 y を 90/99/110/120/130 mm。**モデル変更のみ、実装ゼロ。**
2. **足裏 46 mm を既定にするかの判断** ── 実機で板を作り直せる範囲(アンクル筒が
   既に直径 46 mm なので掃引体積の増加ゼロ)。URDF 2 行 + `profile.rs` の
   `cop_half` 1 行。**ユーザの判断待ち。**
3. **`prox_weight = 0.0`** ── `SolveConfig::default()`(misa-wbc `solve.rs:78`)の
   ままなので、`Solver` セッションを持ちながら毎 tick コールドスタートしている。
   設定値 1 つ。ノイズ床に効く可能性がある(未検証)。
4. **関節の位置・速度制限が QP に無い** ── トルク箱のみ。
   `misa_wbc::tasks::joint_limit_cbf` が未使用。ankle_roll が限界の 196% まで
   押し込まれていた(§18.5)のはこれ。
5. **パルス幅の掃引** ── `PUSH_DT` は 0.10 s 固定。**「力積で刻めば幅は関係ない」
   というベンチの前提そのものが未検証。** 24 run。

**やらなくていいもの**: 角運動量タスク(§21.3 で反証)、着地点補正の再挑戦
(336 点で有害)、分離量の 7 個目探し(§22.5)。

## 6. 罠

- `ARM_PITCH=-1.40` は `FIRST_SWING=0` だと **押しが発火する前に転倒する**。
  全条件が同じ結果になったら、まず `PUSH at` が出ているか確認する(`nofire`)。
- `TORQUE_SCALE` は QP のトルク箱しか動かさない。プラント側は URDF の `effort`
  から焼き込まれる。**両方上げるには URDF を変えるしかない。**
- 足裏を広げるときは **URDF の box と `SOLE_HALF_W`/`cop_half` を必ず一緒に**。
  片方だけだと存在しない足を仮定して計画する。
- MuJoCo は摩擦錐を厳密に守るので、地面基準の摩擦利用率は 1.00 で飽和する。
  「滑ったか」は**大きさではなく時間**で見る。
- 生存は力積に対して**単調でない**。二分探索は使えない(§18.2)。
